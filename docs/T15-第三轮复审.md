## 2. 唯一剩余行为验收缺口：改文本时的 200 行不等于下一次过滤执行时仍在途

**位置：** `tests/settings/settings_data_async_gtk_test.cpp` 的 testContinuousSearch，第 645–672 行附近。

单步泵事件有效地在第一片之后停住，因此改文本之前确实能看到 200/4000。问题是改文本并不会立即执行下一次过滤：GtkSearchEntry 的防抖信号稍后才发生，等待期间旧 idle 继续运行并完成全部 4000 行。

本轮在忽略目录复制当前正式测试，仅增加 GLib signal emission hook，在 `search-changed` 的生产处理函数执行之前记录旧列表行数；未改变生产处理函数或事件时序。观察为：

```text
before_production_filter query=pin   old_rows=20000
round1_before_interrupt_rows=200 expected_total=4000
before_production_filter query=xue   old_rows=4000
round2_before_interrupt_rows=200 expected_total=4000
before_production_filter query=zhong old_rows=4000
```

因此当前测试的两个 200 断言是真实的，但它们位于较早时点；下一次过滤真正执行时旧批次均已完成。这仍不能证明“未完成的 idle 被新过滤取消”。这是一项测试刺激/观察边界缺口，本轮没有发现新的生产搜索回归。

## 3. 已独立验证的最小方案

无需修改 GTK 防抖或生产搜索代码。在测试副本中，仅在两次目标切换设置文本后立即发出真实控件信号：

```cpp
gtk_entry_set_text(GTK_ENTRY(searchEntry), "xue");
g_signal_emit_by_name(searchEntry, "search-changed");
// 逐步泵至 xue 的首片后，再执行同样的 zhong 切换。
```

同样的生产处理函数、同样的旧批次和最终行集合，实测变为：

```text
before_production_filter query=xue   old_rows=200
before_production_filter query=zhong old_rows=200
exit=0
```

该副本的十组测试全部通过，最终词条和 sourceIndex 精确比对仍通过。方案文件在 `immediate_filter_probe.cpp`；它只用于复审演示，没有写入现有测试。

### 正式收尾标准

1. 对两次目标切换，在**下一次生产过滤开始处理之前**断言 `0 < oldRenderedRows < oldExpectedRows`，不能仅在改文本前断言。可沿用 emission hook 或等效受控观察。
2. 用受控控件信号或等效确定性事件调度，使下一次过滤立即发生，避免防抖期间旧批次已经完成；禁止修改生产防抖或另写测试专用过滤算法。
3. 观察两次目标切换即可；同一查询可能有后续控件防抖重复信号，不要把不属于目标切换的重复刷新误判为失败。
4. 保留三轮真实信号、最终完整集合/拼音/词条/sourceIndex、普通构建 <100ms 心跳，以及已有有效的移走磁盘文件后内存搜索测试。
5. 加入上述过滤前断言时，当前“只改文本、等待防抖”的测试刺激应被拒绝；采用已验证的即时信号方案后通过。先记录这组前后对照，再跑当前目标普通/ASAN 回归即可，无需重做全套存储或安装性能验收。
