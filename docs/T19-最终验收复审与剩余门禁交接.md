## 2. G5：是两项明确失败，不能按现报告的原因直接结案

`fresh-clone-exitcode.txt` 为8。原始日志最终列出78项中 **70 Passed、2 Failed、6 Skipped**；6个界面项按安装脚本无头策略跳过，必须单列。

### 2.1 GTest 中是 append 超时

失败用例：`ArchitectureResourceCoordinationTest.T11_A10_AsyncStartupInitialCommitDoesNotBlockInput`。

具体断言在 `tests/core/pinyin_resource_coordination_test.cpp:400`：

```text
Expected: (appendDurationUs) < (5000), actual: 19257 vs 5000
```

此处计时的是 `provider.append("ceshi")`，不是此前的 `writer->enqueueCommit(initialCommit)`。该套 GTest 实际131通过、1失败。虽然用例名称包含“首提交”，分析时仍须准确定位到失败的打字调用；不能据此声称首提交 enqueue 发生了19ms阻塞。

GTest 当时与其他 CTest 并发执行，因此资源竞争是可检验的假设。但当前证据没有 CPU调度、锁等待、I/O 或页缺失分解，不能把竞争写成已证实的唯一根因。
