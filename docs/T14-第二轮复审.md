## 2. S1 / P1：首次启动仍独立读取设置、stamp、Hash，绕过新读取契约

**位置：** `adapter/fcitx5/src/inputmethod.cpp:120–122,396–400,432–440`。

当前初始化路径是：

1. `loadSettings()` 调用新 `SettingsStore::load()`，却只返回 `.settings`，丢掉状态、Hash 和 stamp；
2. 构造函数稍后重新 stat 配置路径；
3. 再调用 `computeFileContentHash(path)` 独立打开路径，作为 `appliedVersion_` 和 runtime.state 的事实；
4. `settingsLoadFailed_` 默认 false，首次读取失败没有进入后续重试状态。

因此，修复加载器仍不足以保证首次启动的应用版本正确。这是上轮 R1/R2 的同一事实边界在初始化路径上的遗漏。

### 2.1 真实 Fcitx 初始化期间原子替换

在引擎首次加载 A（禁用、字号 14）后、构造函数独立计算 Hash 的 fopen 前，将私有配置原子替换成 B（启用、字号 28）。真实 EventLoop 运行 8.3 秒，覆盖后续轮询，再发送真实 n 键：

```text
before_active=0 generation=0
observed_load_opens=3
after_active=0 generation=0 accepted=0 preedit=
runtime: applied_content_hash=f009f7c137e228c6, settings_generation=0
disk_enabled=1 disk_font=28 disk_hash=f009f7c137e228c6
```

构造函数把 A 设置标为 B Hash；第一次轮询虽然读到了 B，却因 Hash 相同跳过应用。随后 stamp 也已更新，旧设置持续生效。runtime.state 会错误表示当前磁盘内容已经应用。

### 2.2 首次读取失败，故障消失但文件不变

同样在真实构造入口，对私有配置的第一次 fopen 注入一次 EACCES，之后所有读取正常，不再修改文件。磁盘始终是禁用配置：

```text
before_active=1 generation=0
observed_load_opens=2
after_active=1 generation=0 accepted=1 preedit=n
runtime: applied_content_hash=08fedaef108b59ee, settings_generation=0
disk_enabled=0 disk_font=14 disk_hash=08fedaef108b59ee
```

首次加载得到的默认设置被标上磁盘禁用配置的 Hash/stamp，后续没有重读。这里的问题不是要求启动时必须存在历史有效配置，而是失败后的默认值被冒充为该文件的成功应用结果，且故障恢复后不收敛。

### 最小目标

- 首次初始化与热载消费同一个成功读取结果中的 settings、status、Hash、stamp；不要另开路径补造“已应用版本”。保留现有公开 API，优先调整既有初始化流程。
- 首次缺文件仍按原默认契约处理。首次 I/O 失败可以保留明确的启动容错，但不得宣称已成功应用磁盘文件；恢复后即使 stamp 不再变化，也要按受控频率重读并收敛。
- 只有成功读取且真正接受的内容可以建立对应的成功应用版本。不要用增加第二个 Hash 或新 Manager 绕过问题。
- 将上面两个真实启动交错固化为确定性失败前/修复后测试，保留本轮已经有效的热载替换、一次失败恢复测试。
