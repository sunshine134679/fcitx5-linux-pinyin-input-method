## 2. R1 / P1：合成锁变量仍能从进程环境绕开真实锁检查

位置：`tools/settings/update_controller.cpp::lookupEnv()`、`UpdateController::isPackageManagerLocked()`。

`lookupEnv(environment, key)` 在显式字典未提供键时仍调用 `std::getenv`。因此即使默认调用 `isPackageManagerLocked()`、传入空 Environment，只要进程继承了 `MODERNIME_PACKAGE_MANAGER_LOCK_FILE` 或 `MODERNIME_PACKAGE_MANAGER_LOCK_DIR`，新函数就只检查那个路径并提前返回 false，跳过真实系统锁。

旧实现的合成文件只会补充正向占锁事实，之后仍检查真实锁。新实现把同一变量变成了替代真实锁来源的开关。这与“无合成字典时保留默认生产保护、无新增绕过”的交付承诺不一致。

### 独立可重现证据

本轮链接现有 update_controller 生产源对象，使用一个仅作用于探针进程的 LD_PRELOAD，将系统锁路径的 open 映射到测试自有的 POSIX 持锁文件。**未打开写入、持有、释放或修改任何真实宿主包锁。** 默认 API 保持空参数，结果如下：

| 合成系统锁状态 | 仅改变探针继承环境 | 默认 API 结果 |
|---|---|---|
| 已占锁 | 无合成锁变量 | locked=1，正确 |
| 已占锁 | MOCK LOCK FILE 指向不存在文件 | **locked=0，跳过系统锁** |
| 已占锁 | MOCK LOCK DIR 指向不存在目录 | **locked=0，跳过系统锁** |
| 未占锁 | 无合成锁变量 | locked=0，正向对照 |

见 `lock-probe-results.json`、`host-held-*.log`、`lock_probe.cpp`、`synthetic_host_lock.c`。

### 最小目标与验收

- 将“替换锁事实来源”限于显式、作用域明确的测试依赖，或仅测试目标启用的接缝；不要让默认生产入口从继承环境选择替代锁根。普通业务配置/启动环境不能关闭真实锁保护。
- 已有只增加保护的 force-locked 行为与替代真实锁来源要区分，禁止为绿灯把真实占锁当未占锁。无需新建 Manager 或全局可变回调体系。
- 测试改用明确注入的合成依赖；当前 update_controller_test.cpp 通过全局 setenv 让整个进程切换锁根，也须随边界修正，不保留进程全局旁路作为最终方案。
- 用私有合成系统锁验证默认生产对象：真实事实占锁时，即使继承 FILE/DIR 指向未锁/缺失路径，仍必须返回占锁。对测试注入则分别验证合成占锁与未占锁、零 spawn、失败释放、旧 ID 和有界结果队列。
- 额外验证合成路径不可读/异常时的明确语义，不能静默回退为无锁。不要触碰宿主真实包管理器或实际调用 apt/dnf/pkexec。

## 3. R2 / P1：性能分段延长快照引用寿命，漏计了原先包含的释放成本

位置：`tests/core/personal_engine_benchmark.cpp::verifyLmdbConcurrentPruningLatency()` 与 `verifyLmdbFirstKeyAfterClearLatency()`。

原测量：

```cpp
const auto start = now();
writer.enqueueCommit(event);
DoNotOptimize(writer.snapshot()->recallCandidates(...));
const auto end = now();
```

临时 shared_ptr 在完整表达式结束时释放，位于 end 之前。若 Worker 在此期间替换快照并释放旧引用，输入侧的最后一次引用释放及对象回收也包含在原总耗时里。

新测量：

```cpp
const auto t0 = now();
writer.enqueueCommit(event);
auto snap = writer.snapshot();
DoNotOptimize(snap->recallCandidates(...));
const auto t3 = now();
// snap 在采样记录后、迭代结束或函数结束时才释放。
```

命名引用把可能昂贵的析构移到 t3 之后。原始问题就包括输入线程快照回收长尾，因此即使数值门限未改，这也改变了被测工作范围。不能把现在的绿灯直接当作相同口径性能已闭环。

本轮最小 C++ 生命周期探针模拟快照在 recall 时失去其他持有者：原表达式测得约12.163ms；命名引用测得0.035us，另有约12.191ms释放发生在计时外。**这是语言生命周期边界的反证，不是声称生产快照析构固定需要12ms，也不据此否定共享空快照的真实收益。** 见 `snapshot_timing_boundary.cpp`、`snapshot-timing-boundary.log`。

### 最小目标与验收

- 保留分段采样，但用内层作用域释放 snap，再记录最终总结束时间，使总墙钟仍覆盖原来所有工作；可单列 release/destruction 段，不能把它排除。
- 并发剪枝与清空首键两个入口都修复计时边界；总门限仍为原5ms/30ms，不减规模、不改剪枝政策、不挑通过轮次。
- 证明释放确实处于计时内的负向样本能被门禁发现，正常产物通过。修正计时后再按既有协议运行规定三轮、完整矩阵、8项超限拒绝自检及 Release 全量，绑定完整输出/退出码/源码与二进制摘要。
- 共享空快照优化可保留。补充现有清空/故障恢复/跨 Writer 隔离与不可变旧快照契约的执行证据；不要为了验证 singleton 写仅断言地址相等的测试。
