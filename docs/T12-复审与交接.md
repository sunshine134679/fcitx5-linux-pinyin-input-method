## 1. 已确认有效的实现

- `refreshPackageCache` / `runSystemUpgrade` 在 spawn 前调用同一个互斥保护的 `tryBeginPackageOperation`，正常等待期也占槽；原先仅在后台追踪期设置 active 的窗口已关闭。
- Starting、Running、Continuing、Uncertain 共用一个状态负责人；超时后台接管沿用原 operationId，没有再次抢槽。
- `advance` / `finish` 校验当前 operationId；旧 ID 不能结束新操作。
- 完成结果队列最多 8 项，开始新操作不会清空旧结果；队列满时拒绝开始，消费后可以恢复开始。
- 同步正常完成、认证失败和 spawn 失败的主要分支通过 `recordUnconsumed=false` 避免重复投递结果；后台完成才保留待消费结果。下述 R1 是其中遗漏的一个分支。
- 独立假命令探针确认：普通等待中被信号终止、超时后在后台被信号终止，均最终进入 Uncertain，继续占槽且不生成伪完成结果。
- 本次差异没有修改 T11 的候选、学习、容量、数据格式或性能门禁代码。

## 2. R1 / P1：同步锁拒绝错误地占用完成结果队列

### 定位与根因

文件：`tools/settings/update_controller.cpp:1076–1080`，函数 `UpdateController::refreshPackageCache`。

检测到外部包管理器锁时，代码执行：

```cpp
finishPackageOperation(*opId, res);
return res;
```

`finishPackageOperation` 的 `recordUnconsumed` 默认是 true。因此同一个失败既同步返回给调用者，又额外成为一个未消费完成结果。对照 `runSystemUpgrade` 的锁拒绝分支，以及刷新函数的缺依赖、spawn 失败、认证失败和成功分支，均明确传入 false。

随后 `package_operation_state.cpp:22` 在未消费结果达到 8 项时拒绝开始新操作。当前 `tools/settings/` 内没有生产调用点消费完成队列；不能假定页面会自动清理这些重复结果。

### 独立复现

探针链接当前 Debug 构建的两个生产对象，没有复制状态机实现。仅使用临时目录的假 apt-get/pkexec，以及现有 `MODERNIME_MOCK_PACKAGE_MANAGER_LOCKED` 测试接口；没有执行真实认证或包事务。

证据：

- `build/t12-review-evidence/locked_refresh_probe.cpp`
- `build/t12-review-evidence/locked_refresh_probe.log`

观察结果：

```text
locked_request=1 success=0 active=0 unconsumed=1
...
locked_request=8 success=0 active=0 unconsumed=8
after_unlock success=0 message=包操作结果队列已满（最多保留8项未消费结果），请先消费已有结果。
sync_failure_redelivered=1
after_manual_consume success=1
probe_exit_code=1
```

这里的退出码 1 表示目标行为验收失败，已成功复现缺陷；不是构建失败。影响是同一进程内的后续包操作被错误背压阻塞，直至显式消费或进程重启。本次没有证据表明它造成用户数据损坏，故定为 P1。

### 最小整改与验收

1. 先补生产控制器行为回归，覆盖连续至少 9 次锁拒绝。
2. 每次拒绝均应失败、释放自己的槽位、未消费结果数不增加、spawnCount 为 0。
3. 解除外部锁后，同一进程内的下一次操作应成功，并只发生 1 次 fake spawn。
4. 预先保留一项真实后台完成结果，重复上述锁拒绝后，它的 ID、结果和一次消费语义必须保持不变；不得通过清空队列修复。
5. 与同步返回契约一致地结束锁拒绝分支，不重复登记待消费结果。无需增加页面自动消费器或新的抽象。
6. 检查刷新/升级全部同步返回分支，防止同类遗漏；保留正常后台完成的结果队列与 8 项上限。

## 3. R2：生命周期测试与验收范围需要补齐
