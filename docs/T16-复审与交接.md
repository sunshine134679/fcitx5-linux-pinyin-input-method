## 3. R1 / P1：CI 的 JUnit 写入路径与读取路径不一致

**位置：** `.github/workflows/ci.yml:43,60,84`；后续读取位于 69–70、89 行。当前协调分支也保留了同样命令。

原命令示例：

```sh
ctest --test-dir build/ci --output-junit build/ci/debug-junit.xml
```

CTest 切入 `--test-dir` 指定目录后解析这个相对输出路径。因此文件实际写到：

```text
build/ci/build/ci/debug-junit.xml
```

后续 `verify_required_tests.py` 却在仓库根读取：

```text
build/ci/debug-junit.xml
```

本轮用一个只运行 `/usr/bin/true` 的最小 CTest 项目，原样执行 CI 路径形式，真实结果为：

```json
{
  "exit": 0,
  "workflow_expected_exists": false,
  "actual_xml_paths": ["build/ci/build/ci/debug-junit.xml"]
}
```

Release 的 `build/ci-performance/release-junit.xml` 和 core-only 的 `build/ci-core-only/junit.xml` 同样重复目录。即使测试本身全部绿色，后续必需测试读取步骤仍会因报告缺失而失败。这个问题不会被普通本机完整 CTest 绿色自动覆盖，因为后者没有执行该 workflow 的报告读写命令。

### 最小修复

三处输出统一使用明确的绝对路径，例如从仓库根执行时：

```sh
ctest --test-dir build/ci --output-junit "$PWD/build/ci/debug-junit.xml"
```

Release、core-only 同样处理，并保持后续读取位置一致。也可以使用相对于测试目录的单独文件名，但不要再次重复 build 目录。

本轮绝对路径正向对照已经生成正确文件并成功解析测试项。修复不得通过关闭 required-tests 步骤、忽略缺报告、减少必需测试或吞掉失败实现。

### 完成标准

1. Debug、Release、core-only 三种 workflow 形式分别写入预期位置，实际 JUnit 存在且可解析。
2. 后续验证工具读取这些同一路径，保留 Debug 功能结果与 Release benchmark 结果的既有组合方式。
3. 保留原相对路径形式会失败的回归对照，防止将“CTest 返回 0”再次误认成“报告已交付”。
4. 修正 CI 文件并记录新提交和本地复验范围。未触发远程 workflow 时如实标记远程 CI NotRun，不声称 GitHub 已绿。
