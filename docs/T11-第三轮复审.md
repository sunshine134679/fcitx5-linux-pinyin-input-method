## 2. F1 / P0：Reloading跳过世代观察，导致新事实丢失和旧视图获Ready授权

### 根因与代码

`core/src/learning_writer.cpp:310–315` 新增：处于Reloading时，`refreshBeforeEnqueue()`直接return。

但Reloading期间仍可能发生外部第二次clear，也可能正处于异步初次加载而尚未取得数据库真实revision。后续 `enqueueCommit():94–115` 继续用旧 `resetRevision_` 给PendingCommit打标；后台 `run():526–528` 正确过滤旧世代事实，结果把实际发生在新代的事实一起丢弃。

发布检查 `run():515` 只比较freshState与内存已观察revision；输入根本没有观察新代时，这个检查无法拒收磁盘上已经过时的结果。

### 已完成的隔离复现

`epoch-probe.cpp`、`epoch-probe.log` 均使用当前Debug核心库与临时SQLite数据库，正常退出。读库由独立LearningStore完成。

1. **加载中第二次clear，尚未到下一次定时轮询。**
   - 正常Writer，暂停worker；clear到epoch1并调用reloadIfChanged进入Reloading。
   - 外部再次clear到epoch2；直接提交合法事实，不额外调用reloadIfChanged。
   - 输入仍标epoch1；恢复worker，flush返回true，但独立库里新事实不存在。
2. **已有非零revision数据库的异步初次加载。**
   - 合成库已经clear过，revision为1，写入5000条基线词。
   - 创建异步Writer，在读取完成、发布前暂停；提交事实。
   - 内存revision仍0，pending队列确实有1条；恢复后flush返回true，独立库新事实不存在。
   - 异步入队返回false表示持久存储尚不可用，不等同于未入队；本复现同时检查队列和最终持久化，不将该返回值本身误报为崩溃。
3. **已读旧结果遇到第二次clear，输入未观察到新代。**
   - epoch1有“旧代词”；worker读完epoch1，在after-read栅栏暂停。
   - 外部clear到epoch2，提交合法事实，放行worker。
   - 生产Ready回调观察到包含“旧代词”的Ready快照，说明旧代被短暂重新授权；最终新事实也未持久化。

同一复现另有 `epoch-enter-probe.cpp` 版本，用契约明确允许的Raw英文 `hello` 事实代替Chinese偏离选择，以避免把“加载期间不可选候选”当作合法触发前提。其输出单独归档。

### 为什么当前测试仍绿

`SecondClearDuringWorkerRebaseRejectsStaleResult` 在第二次clear之后、提交之前显式调用 `writer.reloadIfChanged()`，主动补上生产快速路径跳过的观察，所以不能覆盖这次回归。

`T11_A10_AsyncStartupInitialCommitDoesNotBlockInput` 使用 `options.learningEnabled=true` 创建共享资源，create已经同步建立Writer；随后 `ensureLearningWriter(false)`只是返回既有Writer，根本没有测试异步初次加载。其合成库revision也是0。

新启动Benchmark确实创建异步Writer，但库revision仍0，也没有独立核对最终事实，因而低延迟不能证明清空/保存正确。

### 最小目标与验收

- Reloading不能成为跳过新世代观察的理由。每个允许保存的提交在赋予世代时必须有有效依据；异步初始化的unknown不能当epoch0。
- 不将旧队列事件整体改标为最新epoch。否则清空前的事实会复活。明确未知世代、新代事实、旧代事实的权限和顺序。
- 拒收读取完成之后已经过时的结果；发布仍保持输入锁短临界区。保留快照克隆移出锁等有效优化。
- SQLite与LMDB均加入上述3种场景；输入不先调用reloadIfChanged/page/timer，不靠测试替生产补观察。合法Enter英文、权限切换、频次恰好1、新代首事实、旧词零复活分别验证。
- 正确性恢复后再测真实输入延迟，不能靠少读一次世代取得亚毫秒数字。

## 3. F2 / P1：通知取消尚缺在途调度保证，测试仍在验证另一份实现

生产位置：`adapter/fcitx5/src/inputmethod.cpp:814–825`、析构 `:512–526`。

外层在endpoint锁内取得裸dispatcher指针，随后解锁，才调用schedule。取消/析构也取得同一锁，但它不能收束已经取得指针、尚未调用schedule的线程。调整成员顺序对由宿主独占并销毁的资源有保护作用；若共享Writer或已复制回调寿命跨过宿主，仍需明确保证。当前没有在途计数/等待或覆盖整个调度调用的寿命保护。

**这是静态寿命协议缺口，本轮没有复现生产插件崩溃，不将其写成“ASAN已证实UAF”。** 下一轮应通过真实所有权和交错证明安全，或在实际通知端点修复该窗口，不能仅凭active字段推断已收束。

当前 A07 的“dispatcher”是 `vector<function<void()>>`，回调也是测试函数自行编写；没有绑定生产 `LearningWriter::setOnReadyCallback` 或真正EventDispatcher。A08复制逻辑，采用sleep和局部bool，甚至worker分支中的endpoint->dispatcher从未设为非空，因此可因空指针保护恒定退出，无法证明调度与析构安全。

验收要求：

1. 测试实际生产通知路径；可通过既有Fcitx集成夹具，或将同一通知端点实现供生产和测试共用。禁止在测试里再写一份类似lambda作为被测系统。
2. 确定性暂停于“取得调度器、尚未schedule”和“已schedule、尚未dispatch”两个位置，再取消/销毁；覆盖共享资源仍有持有人和回调已复制的情况。
3. 实际事件循环下，无新按键自动恢复组合/光标/候选；失焦、敏感、reset、二次clear和换会话按当前授权处理。
4. ASAN/可运行的相关并发检查覆盖真实路径。没有编译或未运行的Fcitx通知套件不能由核心TSAN总数代替。
