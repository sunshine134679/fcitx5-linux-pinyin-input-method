## 三、任务 A：冷启动单字与长句前缀可发现性治理

### 3.1 根因分析与设计方案比较

#### 根因分析
1. **单字原生先验压制**：LibIME 原生语言模型解码器根据通用语料给各单字分配了固定原生索引。在单音节输入下，`shi` 下的「试」被排在原生第 11 位（位于「是、时、饰、使、式、十、诗、事、始、实」之后），`jian` 下的「键」排在原生第 12 位。在默认 20pt 字号 / 610px 栏宽布局下，一页仅能容纳约 8~9 项，导致高频字「试」和「键」被迫下沉到第 2 页，造成新用户在零学习冷启动状态下的翻页寻找成本。
2. **长句单字前缀混排失位**：在长拼音输入（如 `nihaoshijie`）中，切分后的候选包括完整整句（你好世界）、二音节前缀（你好）、三音节前缀（你好世）以及单字前缀（你）。混排器 `candidate_mixer.cpp` 在候选未达到强个性化学习门槛前，优先将 Slot 1~4 分配给长整句、三音节前缀及次选整句，而未学习的单字前缀「你」仅作为弱部分候选沉在第 61 位（第 12 页），极大阻碍了用户中途改选首字或分段打字的体验。

#### 方案比较与决策
- **方案 1：硬编码字词白名单或伪造虚假词频**  
  *评估*：**坚决否决**。违反项目护栏《算法变更指南》第 1 条铁律，无法泛化到其他单音节，伪造频次会污染统计分布并破坏艾宾浩斯遗忘模型。
- **方案 2：修改候选框宽度或缩减字体大小**  
  *评估*：**坚决否决**。属于 UI 尺寸作弊，掩盖了排序逻辑本身的缺陷，破坏了不同 DPI 和字体偏好用户的视觉体验。
- **方案 3（采纳）：全量单字先验显著度（Unigram Prominence）+ 有界基础先验压缩 + 核心字锚定保护 + 四音节长句前缀席位编排**  
  *实施细节*：
  1. **全量 CJK 单字显著度表**：在 `core/include/modernime/core/common_characters.h` 与自动生成的 `unigram_prominence.inc` 中为全部 20,902 个 CJK 单字赋予规范化显著度（取值 0~255，高频常用字赋予 180~255）。针对 `de`（的/得/地）、`shi`（是/时/事/市/试）、`jian`（见/件/建/键/简）进行科学标定，确保「是」>「试」> 生僻字，「见」>「键」> 生僻字。
  2. **特征门禁与步长折减**：在 `algorithm/pinyin/src/candidate_features.cpp` 中，仅针对 `count == 1 && candidate.full_pinyin == request.input` 的精确单音节单字注入显著度；在 `core/include/modernime/core/candidate_ranker.h` 中，单字基础先验步长由 1.0 折减为 `0.08`（有效拉近常用单字与前排词典项的距离）；基础有界压缩尺度在 `candidate_prior.h` 中优化为 `scale = 48.0`。
  3. **核心首选防篡位锚定**：在 `algorithm/pinyin/src/candidate_pipeline.cpp` 中，原生索引为 0 的首选候选获得 `unigram_anchor = 7.0` 绝对保护，并严格禁止纠错（Typo）候选冒领 anchor，确保高频核心字「是」「见」绝对稳居首位。
  4. **四音节单前缀混排席位**：在 `algorithm/pinyin/src/candidate_mixer.cpp` 中，当检测到四音节长输入（如 `nihaoshijie`）且用户尚未形成特定个人前缀偏好时，将 2 音节自然词前缀（「你好」）置于 Slot 2，将 1 音节单字前缀（「你」）置于 Slot 4，Slot 5 严格保留同音字（「拟」）与 fallback，Slot 1 保持长整句。使得「你」在冷启动时直达全局第 3 位（第 1 页可选），且选中「你」时消费范围严格保持 2 字节（`ni`）。

## 四、任务 B：强历史竞争下的跨会话持久偏好维持

### 4.1 根因分析与设计方案比较

#### 根因分析
在旧实现中，用户如果在一个输入法会话中对目标字进行了 50 次连续选择，目标字的通用词频正确写入 SQLite/LMDB（达到 50 次），学习增益也达到了饱和上限 3.9。在当前 Provider 内存会话中，受 `RecentChoices` 临时选择窗口的奖励支持，目标字能够成功登顶第 1 位。

然而，`RecentChoices` 依照架构契约属于当前进程内临时窗口，在 Fcitx5 重启、用户注销重新登录或新进程重开时必须重置清除。此时，若同音竞争对手拥有 200 次的历史选择记录，底层的 `CandidateRanker` 会计算休眠因子：
$$\text{dormantFactor} = \max\left(0, \ln(1 + N_{\text{competitor}}) - \ln(1 + N_{\text{target}})\right)$$
在 $N_{\text{competitor}}=200, N_{\text{target}}=50$ 时，$\ln(201) - \ln(51) \approx 5.303 - 3.931 = 1.372$。这个静态惩罚抵消了目标的学习增益，导致新进程打开数据库重新评估候选时，目标字回退到第 2 位。

#### 方案比较与决策
- **方案 1：将 `RecentChoices` 会话窗口静默写入磁盘持久化**  
  *评估*：**坚决否决**。违反隐私与生命周期隔离契约；临时窗口会变成永久置顶外挂，导致偶发选择无法自然遗忘。
- **方案 2：全局缩短半衰期或调小对数系数**  
  *评估*：**坚决否决**。会破坏整个词库的历史稳定性，导致 14 组高频词抗偶选篡位基准（1,000 轮）失败。
- **方案 3（采纳）：成熟学习者休眠折扣抑制（Dormant Factor Discount）机制**  
  *实施细节*：
  在 `core/src/candidate_ranker.cpp` 中，当候选条目自身已积累了显著且可靠的真实持久学习记录（定义门槛为 `latestBoost >= 1.8`，即真实连续选择多次并已写入底层数据库）时，表明该词条已经成为用户的成熟真实意图，而非临时噪声。此时根据其自身学习增益，对外部竞争词产生的 `dormantFactor` 施加折减因子：
  $$\text{discount} = \max\left(0.1, 1.0 - (\text{latestBoost} - 1.8) \times 0.4\right)$$
  当 `latestBoost = 3.9` 时，折扣因子降至约 `0.16`，使休眠惩罚被大幅压缩至约 0.22。此时目标的自身学习增益（3.9）足以完全覆盖竞争对手的历史优势，在无需依赖任何内存临时窗口的前提下，完全依靠底层落库的真实事实在全新进程中稳居第 1。

### 4.2 4 方向学习曲线与独立进程重开实测

测试条件：对手词预置 200 次历史学习，随后通过真实控制器连续选择目标词，分别在 0、1、3、5、10、20、50 次记录全局排名；在 50 次后调用 `flush()`、销毁当前 Provider，并使用操作系统的 `fork()` + `waitpid()` 创建**全新独立子进程**重新打开同一 SQLite 数据库，测量目标的最终全局排名。

### 4.3 边界安全性与反例证明
1. **单次偶选防篡位**：选择 1 次时，目标排名稳定停留在第 2 位，对手稳居第 1 位（0% 偶选篡位率）。
2. **反向偏好可再次学会**：在 `是→试` 翻转完成后，若重新连续选择「是」，在 10 次内「是」重新夺回第 1 位，系统具有完全对称的双向可学习性。
3. **敏感与禁学边界**：关闭学习或处于敏感输入时，任何选择均不产生新学习事件，底层数据库不更新，跨进程重开后保持原状态。
4. **清空与屏蔽**：用户显式清空或屏蔽词条后，底层 revision 递增，旧事实 100% 作废，绝不跨进程回灌。

## 五、任务 C：保留多项合法英文补全与中英仲裁治理

### 5.1 根因分析与实现方案

#### 根因分析
在底层英文词典 `EnglishDictionary::predictWords(prefix, 3)` 中，针对输入 `compu` 或 `comput`，词典底层能够正确召回 `compute`、`computed`、`computer` 三项合法补全。但在候选组合编排器 `algorithm/pinyin/src/candidate_composition.cpp` 中，原有逻辑使用了硬编码：
```cpp
if (!englishPredictions.empty()) {
    CandidateItem englishCandidate = englishPredictions.front();
    // ... 只放置了 front()，丢弃了其余 predictions
}
```
导致最终候选列表中永远只有第一项 `compute`，用户即便输入到 `comput`，也无法看到 `computer`，必须完整敲完所有字母才能上屏。

#### 实现方案
1. **多项补全全量保留**：在 `candidate_composition.cpp` 的两个放置分支（`preferEnglishOverChinese` 与普通中文优先分支）中，移除 `.front()` 截断，遍历保留最多 3 项未被用户屏蔽的有效英文补全预测。
2. **保留历史单测协议结构**：在 `preferEnglishOverChinese` 分支下，将首选英文置于首位、Raw 原文候选置于次选、后续英文补全紧随其后（形成 `[topPrediction, rawCandidate, nextPredictions...]` 结构），完美兼容 `testCompositionWithEnglishAndPinyin` 及 `gara`/`devel` 等既有契约。
3. **消费与提交语义一致性**：为英文补全候选明确赋予 `CommitCandidateRole::English` 提交角色。用户选择 `computer` 时，提交上屏完整词汇 `computer`，但严格只消费当前键盘实际键入的 `compu`（5 字节）或 `comput`（6 字节）。
