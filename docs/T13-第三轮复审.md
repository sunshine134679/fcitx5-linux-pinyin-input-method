## 2. T1 / P1：后台回收器对仍运行的 PID 忙循环

**定位：** `tools/settings/process_runner.cpp:44–86`。

`g_reaperCv.wait_for(..., [] { return !g_pendingReaps.empty(); })` 在队列已有待回收 PID 时立即返回。若 PID 尚未退出、WNOHANG 返回 0，队列保持非空，下一轮又立即复制队列并 waitpid，没有任何退避。因此 30ms 并没有限制实际扫描频率。

**独立复现：** 真实 collector 发布终态后暂停 700ms。父侧业务结果已返回，主线程大部分时间在 sleep；通过 getrusage 测得父进程 CPU 累计约 **694107μs**，与待回收窗口几乎相等，尽管 `unreaped_collectors=0`。这证明“最终零僵尸”不能证明回收期间资源使用正确。Unknown/握手超时路径也会登记仍运行的 collector，等待可能更长。

**目标结构与最小整改：**

- 区分空队列等待新任务和非空队列等待下次回收时机。新任务/停止信号可以唤醒，但“已有未退出 PID”本身不能使轮询持续立即重入。
- 为每轮未完成项安排可解释的有限回收频率；不要在测试里人为减短暂停掩盖问题。
- 明确线程退出及其状态寿命。当前永久 detach 线程引用可析构的静态 mutex/CV/vector；本次未据此宣称已复现崩溃，但修改回收器时应建立安全停止或明确的进程寿命策略，避免依赖静态析构时序。GUI 退出不能 join 正在运行的包命令，也不能杀 collector。
- 保留直接子进程/跨进程 observer 的区分、可靠回收和 Unknown 现场保留，不另建通用 Manager。

**验收：** collector 终态后暂停、Unknown 时仍活着、多个待回收项均不能忙循环；用宽容的 CPU 预算或可观测调度频率上界验证，最终仍零僵尸、资源有界。另覆盖待回收/空队列时退出 GUI，不挂死、不访问已销毁状态、不误杀事务。

## 3. T2 / P1：新 exec 证明通道阻塞在 deadline 之前

**定位：** `process_runner.cpp:1024–1049`，`read(execPipe[0], ...)` 与之后才建立的 startTime/deadline。

零启动证明通道的方向正确，但新增 read 是阻塞调用，且发生在期限开始之前。collector 子进程在成功 exec 或报告失败之前停滞时，父侧没有本路径的期限保护。

**独立复现：** 私有测试钩子只在 fork 子进程执行 execvp 前延迟 650ms；CommandSpec timeout=100ms。实际返回：

```text
state=1 exit=0 timedOut=0 elapsed_ms=683
```

不是原有“exec 后 wrapper 睡眠”测试；本次正好停在新 execPipe 仍开着的窗口。无限停滞会令该 read 无限等待。

**目标与验收：**

- 在启动控制等待前建立一次单调 deadline，让 execPipe 和 handshake 都服从它；用有期限的 poll/nonblocking 状态读取，不把阻塞迁到另一个期限外位置。
- 完整 errno 才是 exec 失败证明，正确处理 EINTR、EOF、部分消息及期限到达；不能为修期限重新把未知状态当 NotStarted。
- 超过期限但没有零启动证明时，返回保守的 Unknown/Uncertain、保留引用，不杀可能已经启动的包命令。
- 加 pre-exec 延迟/停滞、真实 exec 失败、成功 exec 后握手延迟、目标已启动后 collector 崩溃等测试，100ms 的等待应在明确容差内返回，既有零 spawn 与占槽证明仍成立。

## 4. T3 / P1：数字先窄化再校验，可把错误退出码和 PID 变成合法值

**定位：** `process_runner.cpp:578–588`，collectorPid/childPid/exitStatus 从 long long 到 pid_t/int 的直接转换。

字段虽然已经确认是 Number，但转换前没有验证目标类型和协议允许范围。当前平台上越界值会窄化，后面的 PID 比对或 exitStatus 判断看到的是转换后的值。

**独立复现：** 使用当前真实 waitForOperation/parseStateFile，合法 JSON、已登记引用、其余必需字段齐全：

- `exitStatus=4294967296` 被转换成 0，返回 `state=Exited exit=0`。
- `collectorPid=期望PID+4294967296` 被转换回期望 PID，也返回 `state=Exited exit=0`。

因此仍能将错误状态授权为成功，或绕过刚增加的 PID 数字一致性检查。本次只验证协议错误接受，没有执行真实包操作或宣称实际 PID 重用攻击。

**目标与验收：**

- 对每个数字在转换前验证表示范围和业务范围；退出码、PID、计数及峰值不能以窄化或回绕修复输入。
- 已确认 Exited 的退出码应符合真实退出事实；Starting/Running/Unknown 的允许值与子 PID 组合按明确协议检查。更新合成夹具使其符合协议，保留其原有行为断言。
- 测试 target-type 边界、正负越界、退出码域外值、PID 加 2^32、正常退出码 0/非零及 Unknown 的正确值。错误输入不得授权完成或清目录。
- 无需重写 Lexer 或增加后端抽象，收敛在协议解码边界即可。
