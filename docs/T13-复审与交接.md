## 2. 已确认问题

### R1 / P0：状态发布失败时仍启动事务，随后把未知状态当退出并释放槽位

**定位：** `tools/settings/process_runner.cpp:779–869`、`:654–669`；`tools/settings/update_controller.cpp:468–482`。

collector 先 fork 目标命令，再发布初始 state.json；`writeAtomically` 的返回值被忽略，随后无条件发握手成功字节。父侧超时后只判断 `ps.childPid > 0 && isPidAlive(...)`，状态缺失或不可解析时 childPid 默认为 0，代码返回 Exited。控制器据此 finish 并释放操作。

**独立复现：** 在私有测试目录中用启动 wrapper 在执行真实 collector 前创建同名 state.json 目录，确定性阻止状态原子 rename，模拟状态发布失败。实际运行的 collector 与控制器均未替换实现。假命令写 start 标记，运行约 1 秒后写 done；包等待设为 100ms。

```text
target_done_when_controller_returned=0
request=0 success=0 active=0 phase=0 ... 子进程已退出 ...
next_slot_accepted=1
```

控制器返回时假事务未结束，却回到 Idle 并允许新操作。这是已复现的错误授权边界；没有执行真实包事务或声称已造成真实系统损坏。

**整改：**

- 将初始化、允许目标执行、启动确认、终态发布明确区分。关键准备/状态写入失败不能忽略；能够证明未启动才返回 NotStarted。目标可能已启动但握手/发布不确定时返回 Unknown，保持同 ID 的 Uncertain，不强杀包命令来迁就初始化流程。
- Exited 必须来自当前操作的完整、有效终态及真实退出事实；不能从缺失 childPid、kill(pid,0) 失败或缺失状态推导退出。
- Running 应对应真实启动确认，不能在进入执行器前就无条件宣告已运行。
- 检查初始/终态和 tail 写入的失败传播，避免发布“成功结果已交付”而结果文件尚未完整就绪。
- `startBackgroundPackageTracking` 当前仅 wait 一次 300000ms，任何非 Exited 都转 Uncertain 后结束观察；其中 Continuing 仍代表已知继续运行，不应只因第二次等待到期丢失最终完成观察。该分支为静态确认，本次未运行十分钟等待；用可控期限/时钟测试补齐。

**完成标准：** 初始化失败且确认零执行时零 spawn；一旦可能已启动，故障期间槽位不释放、重复请求零 spawn；恢复或真实终态到达后只交付一次。多轮 Continuing 后最终仍能正确完成。

### R2 / P1：operationId 不足以跨会话识别事务，旧目录和非完整状态被接受

**定位：** `process_runner.cpp:181–234`、`:1066–1137`，以及 `:53–77` 的 PID 存活判断。

本地 map 找不到 ID 时，`waitForOperation` 扫描整个 TMPDIR，按 ID 前缀挑 mtime 最新目录。T12 ID 是进程内自增值，不是跨会话唯一身份。状态解析只做字符串查找，valid 仅要求 state 非空、ID 非零；并未验证完整 JSON、字段类型、大小未被截断或 collector 的启动身份。

**独立复现：** 在全新探针进程、空 map 中预置私有 TMPDIR 的历史同 ID 目录及 `OLD_SESSION_RESULT`，不启动任何当前事务：

```text
stale_id_directory_accepted: state=1 exit=0 ... stdout=OLD_SESSION_RESULT
malformed_state_accepted: state=1 exit=0 ... stdout=OLD_SESSION_RESULT
```

第二次连 JSON 花括号都没有，仍被接受为 Exited/0。这里验证的是错误身份/解析接受，不是伪造真实 PID 重用实验；当前代码也未记录可验证的 PID 启动身份。常规进程内路径已有 map 引用，不一定经过目录扫描；本项不宣称所有普通操作都会串会话。已支持的跨进程观察及损坏状态拒收契约失败，按 P1 验收阻断处理。

**整改：**

- 为具体运行建立不可混淆的操作引用：精确私有目录、会话/操作随机 token、operationId 与 collector 身份。进程内 ID→引用映射是运输资源索引，不增加第二套业务状态机。
- 进程内 wait 使用已登记引用；跨进程观察必须显式传递或验证相同引用。没有可信引用时 Unknown；禁止按 ID/mtime 猜目录。
- 严格验证有界完整状态、必需字段、合法阶段、ID/token/身份。文件超限、残缺、重复冲突字段或类型错误均不能当 Exited。无需强制引入新的 JSON 依赖。
- PID 存活只作辅助观察，不能替代同一进程身份；可选择已拥有的进程句柄、pidfd 或启动标识等机制，需覆盖旧 PID/旧状态。

**完成标准：** 同 ID 的两个会话、旧目录 mtime 更新、错误 token、错误进程身份、残缺/超限状态都无法授权当前操作完成；正确引用仍支持 GUI 父退出后的观察。

### R3 / P1：leader 退出就关闭包输出管道，仍存活后代写入 EPIPE

**定位：** `process_runner.cpp:981–1039`。

collector 发现 leader 退出后只做一次非阻塞排空便 break，关闭两流读端并发布 Exited。后代继承写端并稍后输出时，读取者已经退出。忽略 SIGPIPE 不能让 EPIPE 写入成功。

**独立复现：** 假包 leader fork 后立即退出；后代等待约 350ms 再写两流。collector 先返回 Exited/0，后代记录 `write_errno=32`（EPIPE），晚到输出丢失。现有 A06 测的是 GUI 父退出后目标自身输出，没有派生仍持有 FD 的目标后代，未覆盖这个边界。

**整改与完成标准：** 区分 Query 的有界收尾与 PackageTransaction 的持续采集。包模式在已知后代仍持有输出期间继续拥有读取者，不用 leader 退出立即关闭；GUI 真退出、leader 真退出和后代晚输出应在同一个场景覆盖，两流尾部与完成标记保留，零 SIGPIPE/EPIPE。若状态无法确认，保持保守状态；不能为避免无限后代而杀包事务或伪报完成。

### R4 / P1：每次完成都留下 collector 僵尸及永久操作目录，资源没有生命周期上界

**定位：** `process_runner.cpp:23–24`、`:513–525`、`:559–609` 和终态返回路径；控制器 finish/结果消费路径。

成功派生的 collector 没有由 GUI 回收；唯一 collector waitpid 出现在握手失败分支且仅 WNOHANG 一次。map 条目从未 erase，操作目录/spec/diag/tail/state 也没有完成后的释放接口或清理路径。

**独立复现：** 同一进程通过生产刷新控制器连续完成 10 次假同步操作，每次成功且未消费队列为 0：

```text
unreaped_collectors=10
retained_directories=10
retained_files=60
```

`unreaped_collectors` 是探针通过 waitpid 回收到的已完成直接子进程数量；在此之前生产实现未回收。即使每流单文件有界，反复操作的全局留存仍无界。

**整改：** 为 collector 进程、操作引用、目录、输出结果设明确释放责任。同步结果交付后可以释放运输资源；异步结果先转移到有界完成队列，再释放不再需要的运输资源；消费完成结果释放其持有资源。观察者/GUI 销毁不能删除运行中或 Unknown 事务，也不能等待正在运行的包事务阻塞退出。

**完成标准：** 连续成功/失败/超时恢复/消费操作后，僵尸为 0，map 和目录数量在既定保留政策内，不随已完成且已消费操作次数增长；未消费 8 项不被清理，正在运行/Unknown 资源不被误删，GUI 退出仍不杀事务。

### R5 / P1：期限不覆盖完整生命周期，提前 EOF 会误杀合法查询，握手可无限阻塞

**定位：** `process_runner.cpp:344`、`:473–485`、`:596–614`。

查询循环只在输出流开放期间检查 deadline。双流提前 EOF 后，代码另外等 50×10ms，随后 SIGKILL leader，与原 CommandSpec 的期限无关，也不设置 timedOut。包模式则在无期限的握手 read 完成后才开始计时。

**独立复现：**

- Query timeout=2000ms，假命令先关闭双流、正常工作 1000ms：约 514ms 就被杀，结果 Exited、exit=-1、timedOut=false。
- Package timeout=100ms，假 collector 延迟约 600ms 才关闭握手：约 603ms 才返回；若不关闭则没有本路径的期限保护。

**整改与完成标准：** 区分输出 EOF 和进程完成，以单调 deadline 驱动启动/握手/读取/回收；查询在期限内可以关闭输出后继续正常执行，超时才按查询规则处理且正确标记。握手有期限且遵守 R1 的“可能已启动则 Unknown”规则。连续大输出的读取批次也必须让出机会检查期限和另一流，不能由无限 read 循环绕过调度。

### R6 / P1：Environment 从覆盖项变为替换整个环境，发生未声明兼容性变化

**定位：** `process_runner.cpp:286–317`、`:809–840`；对照原 GSubprocessLauncher 的继承加覆盖行为。

新实现只组装 LC_ALL、LANG、PATH 和显式 Environment 项。未显式列出的父环境全部丢弃。生产 `runtimeEnvironment` 仅补入部分显示/会话及 addon 路径，是覆盖项集合，并不包含 HOME、XAUTHORITY、代理等完整环境。不能声称 GUI 的 DISPLAY/DBus 一定丢失，因为部分已显式传入，但未列出的环境语义已经改变。

**独立复现：** 父进程设置一个合成 sentinel，不传同名覆盖项；Query 与 Package 中的 printenv 均退出 1。原启动机制会继承该值。本次没有执行真实认证，不能据此宣称所有 polkit 会话都失败。

**整改与完成标准：** 明确并保持现有 Environment 的覆盖语义，构建适当的环境快照后应用显式覆盖、路径与 locale 政策；不把完整环境打印出来。验证默认继承、显式覆盖、所需 HOME/会话/代理变量和 locale/PATH，避免重复同名 key 导致顺序不明。若要主动收紧环境政策，必须单独说明允许差异并验证真实需要的变量，不能静默改变兼容 API 的含义。

邻近结构风险：GUI 多线程进程 fork 后仍在子进程中分配 C++ vector/string 和调用库函数。调整启动实现时应在父侧准备 argv/env，采用合适的 spawn 机制或让 fork 后路径仅执行必要的安全操作；本次没有据此宣称已复现死锁，也不另计一个发现。
