## 二、第六轮缺陷物理根因修复详情

### 1. R6-01 · P1：按程序 payload 清单与事务变更归属限定恢复范围，杜绝覆盖或删除独立用户新数据
- **缺陷现象**：当 `--target-prefix` 与用户数据目录重合（例如 `--target-prefix=$HOME/.local`，导致 `$target_prefix/share/modernime` 即为默认 `$data_dir`）时，前版迁移脚本将整个 `share/modernime` 目录复制进备份，并在回滚清理时将未出现在迁移前清单的文件全部删除、回滚时用备份全量覆盖。导致迁移期间由独立用户进程写入的既存文件修改（如 `owned-user-data` 由 `old-user-fact` 改为 `new-user-fact`）被回拨覆盖，新建的用户文件（如 `user-dictionary.txt`）被无故删除。
- **根因分析**：
  1. 目标备份与清理混淆了“程序安装 payload 资产”与“用户数据/配置资产”的边界。
  2. 迁移前不存在的路径，不等于本次包事务创建的路径，不能简单依据“是否在迁移前清单”做非黑即白的粗暴删除。
- **治理实施**：
  1. 在 `scripts/modernime-migrate-channel` 中确立程序 payload 与用户资产的安全隔离边界，实现 `modernime_is_user_data_path` 判定函数：
     - 用户配置目录 `$config_dir` 下的所有文件严格判定为用户配置；
     - 用户数据目录 `$data_dir` 下，除明确属于 ModernIME 程序 payload 的合法发布清单路径（`install-channel.txt`、`install-manifest.txt`、`install_lifecycle.sh`、`pinyin/*`、`managed-files/*`、`extensions/*`）外，其余所有文件（如 `user-dictionary.txt`、`learning.sqlite3*`、`learning.lmdb*`、`backups/*`、`owned-user-data` 等）**严格判定为独立用户数据**；
     - 全局防御：任何文件基名为用户数据典型文件时均视为用户数据。
  2. **预备份阶段**：在遍历目标候选文件与目录时，通过 `modernime_is_user_data_path` 严格过滤。凡判定为用户数据的文件，**绝不记录入 `target_preexisting_list`，绝不拷贝进 `target_backup_dir`**。即使目标目录与数据目录完全重合，用户数据也绝不会被作为旧版本快照沉淀进程序回滚备份中。
  3. **清理新增路径阶段 (`cleanup_target_prefix_files`)**：
     - 若 `$pfx/share/modernime` 是数据目录（或包含用户数据），严禁整目录 `rm -rf`；
     - 深度遍历扫描时，凡命中 `modernime_is_user_data_path` 的条目（如迁移过程中独立写入或新建的 `user-dictionary.txt`、`owned-user-data`）**一律跳过清理，绝不删除**；仅清理本次事务新增的程序 payload 条目。
  4. **回滚恢复阶段 (`restore_original_channel`)**：
     - 因 `target_backup_dir` 中物理排除了用户数据，后续恢复复制仅还原真实的程序文件与旧插件，**绝不覆盖独立用户新数据**；
     - 独立用户数据与自定义词典的生命周期交由 `modernime-data-guard` 专职保护与校验，职责彻底分离。
- **验证结论**：
  - 运行 `python3 build/architecture-sixth-acceptance-20261027/installer/第六轮数据重合与恢复故障探针.py`：
    - `repository_default_data_overlap`：PASS（`owned_value=new-user-fact`，`new_dictionary_value=xin\t新词\t1\n`，`new_dictionary_exists=true`，exit 1）；
    - `generated_default_data_overlap`：PASS（生成包入口表现完全一致）；
    - `data_outside_target` 对照与 `fifth_control` 对照均 PASS。

### 2. R6-02 · P2：真实监控目标恢复 I/O 结果，失败时完整保留恢复材料与事务记录并可见报错
- **缺陷现象**：在 `restore_original_channel` 中，目标前态恢复复制执行 `cp -a --remove-destination -- "$target_backup_dir/." "$target_prefix/" 2>/dev/null || true`，静默丢弃了 stderr 错误信息并用 `|| true` 吞掉非零退出码；随后无条件执行 `rm -rf -- "$temp_work"`，导致复制发生 I/O 错误（如磁盘满、权限异常或注入故障）时，目标文件仍处于损坏或改写状态，但用于恢复的备份材料已被彻底销毁，且向 stderr 输出了可能误导的恢复提示。
- **根因分析**：回滚操作缺乏真实状态收集与 Fail-Closed 事务防卫；在未确认所有目标恢复步骤物理成功前提前销毁了工作目录。
- **治理实施**：
  1. 移除 `2>/dev/null || true`，引入 `target_restore_failed`、`source_restore_failed` 与 `rollback_failed` 状态标志；
  2. 若 `target_backup_dir` 存在且非空，捕获 `cp -a --remove-destination` 的真实退出码与 stderr 日志（记录至 `$temp_work/target_restore_cp.err`）；
  3. 当复制发生任何非零失败时：
     - 设置 `target_restore_failed=true`、`rollback_failed=true`；
     - 向 stderr 明确输出错误：`[ROLLBACK] Error: Failed to restore target backup files from %s to %s`，并回显具体错误详情；
     - 明确告警未完成恢复的目标前缀：`[ROLLBACK] Warning: Rollback encountered errors; original installation may not be fully restored.`；
     - **完整保留事务材料与备份目录**：向用户输出 `[ROLLBACK] Transaction materials and backups preserved at: %s`，并提供定位路径；
     - **严格跳过 `rm -rf -- "$temp_work"`**；
     - **严禁输出 `Original installation restored (channel=script, ...)`** 虚假成功文案；
     - 失败函数返回非零状态（`return 1`），脚本最终以非零码（exit 1）退出。
- **验证结论**：
  - 运行 `python3 build/architecture-sixth-acceptance-20261027/installer/第六轮数据重合与恢复故障探针.py`：
    - `repository_target_restore_cp_failure`：PASS（`injection_hit=true`，`remaining_transactions` 非空保留，`claims_restored=false`，exit 1）；
    - `generated_target_restore_cp_failure`：PASS（生成包入口表现完全一致）。
