## 2. S1 / P0：目标已启动，collector 在握手前崩溃，仍返回 NotStarted 并释放槽

**定位：** `tools/settings/process_runner.cpp:800–820`；目标启动及发 R 的路径 `:1089–1151`；控制器 NotStarted→finish 分支。

握手 EOF/失败后，只要 waitpid 得到 collector 退出或认为其不存活，就删除目录、清引用并返回 NotStarted。collector 的死亡不能证明目标从未启动：目标 fork 与 R 握手之间仍有崩溃窗口，且 Running 状态可能已经写出。

**独立复现：** 使用当前真实 `modernime-settings` collector，私有 LD_PRELOAD 钩子只在其向握手写入 R 前退出 collector，不替换执行器实现。假目标先写 started，1 秒后写 done。控制器返回瞬间记录：

```text
target_done_when_controller_returned=0
request=0 success=0 active=0 phase=0 ... Collector process failed to start or handshake
next_slot_accepted=1
```

目标已经运行、仍未完成，操作却回到 Idle，复现了前轮 R1 的核心错误授权边界。现有 R02 只测“wrapper 睡眠，超时后仍活着”，没有测目标启动后的 collector 死亡。

**最小目标：**

- NotStarted 需要明确的零启动证明，例如有效 N 或独立的 collector exec 失败证据；不能把握手 EOF、退出码 127 或 collector 死亡本身作为零启动证明。
- 目标可能已启动、启动确认丢失时，保留引用，返回 Unknown，控制器保持同 ID 的 Uncertain，拒绝新事务。
- 建立可以区分“未执行许可”与“可能执行”的启动协议，检查每个确认窗口。不能为了消除不确定性杀包命令或删除其控制目录。
- 顺带将 GUI fork 后才构造的 collector cArgs/cArgv 移到父侧，或采用适合的 spawn 机制。当前 Query/目标参数已提前准备，但 collector 启动参数仍在 fork 后分配；本次未声称复现了该类死锁。

**验收：** 实际 collector 分别在目标 fork 后、Running 发布后、R 写出前崩溃；目标仍活着时零新槽/零重复 spawn，不报 NotStarted，不删运行/未知资源。无法 exec collector 的场景仍须正确返回 NotStarted、目标零 spawn。

## 3. S2 / P1：花括号加字段查找仍非严格状态协议，collector 身份未校验

**定位：** `process_runner.cpp:286–404`、`:1314–1350`；`OperationRef`。

新 parser 只检查首尾花括号，然后按子串找 key。数字允许合法前缀后跟垃圾，boolean 允许 true/false 后跟其它字符；没有解析完整语法或冲突字段。fColl/fChild 被读取，却不在必需字段检查中；状态内 collectorPid 没有与 OperationRef 比对，引用也没有可验证的进程启动身份。

**独立复现：** 使用明确登记的私有 OperationRef，分别提供：

1. 完整 JSON，但 collectorPid 与引用不符；
2. 外有花括号、字段之间没有逗号的非 JSON 文本；
3. 包含 `exitStatus: 0garbage` 和 `stdoutTruncated: falsejunk` 的错误文本。

三者均返回 `state=1 exit=0 stdout=SHOULD_NOT_BE_ACCEPTED`，并进入结果清理路径。这个复现不依赖前轮已删除的目录扫描。

**目标与验收：**

- 使用真正完整、有界的结构解析；拒绝错误语法、重复冲突 key、字段缺失、非法类型/数值范围、无效阶段组合、超限或残缺状态。
- 验证 ID、token、collector 身份与可信引用一致；PID 存活不是启动身份。正确的跨进程导出引用继续可用，错误身份不能授权完成或清目录。
- 不要求引入某个特定 JSON 库，但不能继续追加 find/if 充当完整解析器；若改协议编码，应保持内部协议显式版本与严格校验，不修改用户数据格式。
- 未知/损坏状态不能读取成成功，不能影响其它操作资源。

## 4. S3 / P1：新加的 collector 硬截止重新造成 EPIPE，Z 主线程分支又绕过等待期限

### 4.1 采集器寿命不能等同于 GUI 等待期限

**定位：** `process_runner.cpp:1167–1180`、`:1276–1309`。

collector 使用 `max(timeoutMs * 2, 600000u)` 作为采集截止。默认包等待 300 秒，对应 10 分钟后停止排空并关闭两流；此时真实命令或输出后代可能仍在运行。之后阻塞 waitpid 也不能修复已关闭输出的 EPIPE。

**独立复现：** 私有钩子仅加速真实 collector 的 CLOCK_MONOTONIC，模拟越过代码中的 600000ms 边界；目标和宿主时钟不变，没有真实等待十分钟。假目标随后写双流，观察：

```text
state=1 exit=0 timedOut=0 ... stdout= stderr=
target_write_result=write_errno=32
```

采集停止造成 EPIPE，collector 仍可把捕获不完整的场景报告为成功。现有 350ms 后代测试未跨越硬截止。

**目标：** GUI 等待期限只控制返回 Continuing，不控制包输出读取者寿命。删除未经契约授权的采集硬截止；collector 应持续有界排空至真实协议允许收尾。不用延长成另一个任意常量、停止读取或杀包命令替代修复。

### 4.2 主线程 Z 不等于整个进程结束

**定位：** `process_runner.cpp:915–933`。

父侧在超时后用 `/proc` 主线程 Z 状态决定 Exited，再阻塞 waitpid collector 并使用旧 Running 状态的 exitStatus。多线程假命令的主线程 pthread_exit，而工作线程继续 800ms：指定等待 60ms，实际约 816ms 返回 Exited、exit=-1；命令真实正常结束应为 0。

**目标与验收：** 不从主线程 Z 推导整个事务终态，终态和退出码来自 collector 的有效退出事实；到等待期限仍在执行则同 ID Continuing。测试覆盖：长事务跨过原采集硬截止、后代晚输出、主线程退出而其它线程继续、输出已关闭但真实命令仍运行；不超时强杀包事务，不用阻塞回收绕过期限。

## 5. S4 / P1：异步终态先发布、collector 后退出时仍丢失回收责任

**定位：** `process_runner.cpp:1333–1349`；正常同步路径已不同，不能用同步回收测试代替异步。

`waitForOperation(ref)` 读到 Exited 后仅调用一次 waitpid(WNOHANG)，无论是否实际回收都删目录、清 map 并返回。collector 若尚未退出，之后再没有持有者负责回收。

**独立复现：** 真实 collector 的最终 state.json 成功 rename 后暂停 700ms，模拟终态发布与进程退出的合法时间差。生产 waitForOperation 返回：

```text
initial=2 final=1 ref_remaining=0 collector_alive_at_return=1
unreaped_collectors=1
```

probe 最后 waitpid 回收到了这一个遗留直接子进程，生产代码没有回收它。现有 R06 只验证同步刷新。

**目标与验收：**

- 一次 WNOHANG 返回 0 不能算完成回收。保留或明确移交 PID 回收责任，直至成功回收；业务结果可先交付到有界队列，但运输/进程资源仍有负责人。
- 区分实际父进程的回收责任和跨进程只读 observer；不能对不属于自己的 PID/其它会话进程执行错误等待。
- 不让 GUI 关闭等待仍运行的事务，不删除 Unknown/运行中状态，不因结果已消费丢失回收者。
- 加终态发布后暂停/栅栏测试，反复异步完成及结果消费后零僵尸、引用/目录按明确政策有界；保留同步零泄漏、8 项未消费结果和 GUI 父退出回归。
