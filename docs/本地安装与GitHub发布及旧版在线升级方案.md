# 本地安装与 GitHub 发布及旧版在线升级方案

> 执行者：现有协调者。按 `superpowers:executing-plans` 逐项执行，不增加并行实现者。本文件是发布准备与验收方案，尚未执行本机安装、推送、打标签或发布。

**目标：** 将已整合的架构整改形成可安装、可追溯的新正式版，并验证上一正式版用户沿原有入口升级后的数据与使用连续性。

**方式：** 沿用现有 GitHub Release、APT/DNF 签名仓库、Pages 官网及安装生命周期，不另造更新框架。先完成版本/文档/升级兼容准备和隔离演练，再在具体发布候选可审阅后确认本机部署及公开动作，最后验收线上真实更新。

**工具与既有规范：** CMake/CPack、GitHub Actions、APT/DNF、GPG、现有 shell/Python/网站测试；规格依据为本轮用户要求、`AGENTS.md`、[发布维护指南.md](发布维护指南.md)及已有 T19/G6 交付边界。

## 2. 全局约束与发布验收重点

- 保留生产候选排序、容量、用户数据格式和原生 5ms/30ms 等性能门限；不恢复已关闭的架构整改任务。
- 使用新版本号。若远程正式版和标签仍允许，推荐 `0.1.14`；执行前确认远程没有占用/更高版本，不覆盖或移动 `v0.1.13`。
- 版本一旦变化，记录新发布候选 SHA 与原验收 SHA 的差异；不能将旧版测试结果直接重标为新 SHA 全部重跑。
- 新文档/提交中文命名；固定协议入口、资产名、脚本、目标名及 Release 标签格式保持兼容。发布说明可使用中文实体 `docs/releases/v0.1.14-发布说明.md`，既有工作流入口 `docs/releases/v0.1.14.md` 指向同一正文，避免两份事实。
- 所有重量级本地操作持 `/home/wsl/ModernIME/build/parallel-control-20261017/machine.lock`；升级试验使用私有 HOME/XDG、真实 `/tmp` 私有目录及容器/虚拟机，不在宿主跑假包管理事务。
- 不删除旧包、历史索引和签名信任入口；不使用临时测试密钥签生产源，不打印私钥、口令或令牌。测试源与测试密钥仅限隔离沙箱。
- 在执行发布前展示新版本、提交、目标仓库、拟执行动作及风险/回退；此前“不推送、不发布”的约束不能因本方案落盘自动解除。

最容易遗漏的五类验收对象：真实旧客户端及旧信任配置；脚本与原生包渠道差异；部署旧索引被缓存或回写；下载/认证/锁失败时用户数据与事务状态；文件已更新但正在运行的插件仍是旧 inode。

## 5. 任务三：真实上一版到新候选的隔离升级演练

- [ ] 脚本/便携：验证其已有“下载新版安装器/源码更新”及迁移入口。当前旧客户端本身拒绝包管理覆盖，因此不得宣称无需迁移的一键包升级。若用户要求脚本渠道也必须在旧 GUI 中无迁移直升，先报告旧客户端限制及是否存在可兼容的旧在线入口；不能靠只改新版 GUI 或静默跨渠道覆盖兑现承诺。

- [ ] 完成来源清晰的新候选必要回归。版本/文档变化可复用无影响的历史检测，但新的更新或安装脚本变更要验证实际分支，并按 AGENTS 执行必要 CTest、全新克隆安装卸载及包门禁。串行执行，不循环挑选最好结果。

**完成标准：** 已支持原生渠道的真实旧客户端能够发现并升级新版，旧信任配置有效、数据保留；脚本渠道边界和未运行平台明确列出。此阶段的“隔离演练通过”不等于“公网升级已经通过”。
