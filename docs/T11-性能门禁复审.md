## 2. 唯一新增硬阻断：Release延迟门禁被预处理掉

### 编译配置与代码冲突

`tests/CMakeLists.txt:1–7` 为保留测试断言，对测试目标使用 `-UNDEBUG`。当前Release基准真实编译标志为：

```text
-O3 -DNDEBUG -std=c++20 -UNDEBUG ...
```

后面的 `-UNDEBUG` 取消前面的 `-DNDEBUG`。但 `tests/core/personal_engine_benchmark.cpp` 将快照、繁忙/并发Writer、LMDB Writer/剪枝、首观察者、清空首键、启学首提交等延迟检查放在 `#ifdef NDEBUG` 内。

结果：**这些延迟拒绝分支在当前Release目标中根本不存在**。原精确查询等少数不受该条件保护的门禁仍存在；不是所有基准检查都被关闭。

按当前Release宏和include路径预处理实际源码，检查结果保存在 `release-gate-check.log`；快照、Writer并发、LMDB剪枝、观察者、清空首键与启学超限错误分支均缺失，而原Hot-path查询超限分支保留。实际flags也另存为 `release-benchmark-flags.txt`。

这里需要更正此前审查中按退出码给出的“Release性能门禁通过”：退出0只能证明编译进去的检查通过，不能证明被取消的检查执行。之前几轮未识别出该宏冲突，本轮已定位。

### 原始日志已经有一次超限

`build/t11-fourth-review-evidence/performance-run-3.log:24`：

```text
LMDB concurrent write/pruning: enqueue+next recall P99=3946.21 us, maximum=34615.95 us
```

P99符合5ms，但max为 **34.61595ms**，超过原 **max<30ms** 门限。因此“三轮全部达标”的声明不成立；报告表也遗漏了这项max，不能只列符合要求的指标。

单次超限可能来自调度干扰，也可能来自真实等待，本轮没有据此断言算法必须重构。需要先恢复实际门禁，在无并行编译/测试负载的条件下完整复测，并保留这次失败记录。

## 3. 最小整改与完成标准

1. **将性能门禁是否启用与NDEBUG解耦。** 保留测试断言有效；用明确的性能验收profile或目标编译定义控制Release门禁。Debug计时不用于Release准入，core-only按其实际构建profile处理。
2. **证明实际Release目标超限会失败。** 用同一基准可执行文件的最小超限自检，或实际调用同一阈值检查路径的负向测试；注入超过阈值的确定性样本应非0退出。另写一份相似if不能证明原目标门禁已启用。检查所有NDEBUG包裹的性能关卡，不只修剪枝一处。
3. **重新串行执行完整三轮Release性能。** 保存构建配置、命令、每轮退出码及完整原始日志。原召回<1ms、更新/下一召回<5ms、竞争P99<5ms且max<30ms均保持。不能增加阈值、删除max、剔除失败样本或改变生产剪枝政策。
4. **处理超限。** 若改善隔离后通过，说明调度条件与复测结果，保留历史失败；若仍失败，测量定位实际等待，仅修已证实的原因。禁止重新大改Writer/排序来追求漂亮数字。
5. **纠正验收报告。** 完整列出各轮Writer及竞争场景P99/max，明确旧日志哪些门禁未执行、哪轮超限。使用Pass/Fail/Skipped/Blocked/NotRun，不以“程序退出0”代替性能判定。正式验收不使用跳过测试安装选项。

通过标准：V1–V3维持关闭；实际Release目标的负向门禁检查有效；完整三轮均满足原门限；受影响功能/构建检查无回归；证据与最终源码/配置相符。物理桌面未完成时写“自动验收通过，桌面待验”，不能称桌面完全覆盖。
