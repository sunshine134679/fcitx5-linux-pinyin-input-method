## 1. P1：敏感模式仍把输入计入共享造词统计

**实际复现**：控制器 `setSensitive(true)` 后分步输入 `王 → 绍 → 龙` 两遍；退出敏感模式并重置后，只正常输入一遍。数据库出现 `王绍龙 / wangshaolong / frequency=3`，以及 `王绍`、`绍龙` 两个短词。对照组仅正常输入一遍，不出现这些合成词。

**根因**：`algorithm/pinyin/src/pinyin_candidate_provider.cpp:1457` 的 partial/final/跨组合造词跟踪无条件运行；`learningEnabled_` 只在 `learningWriter()` 阻断落库。共享 `phraseStats` 仍然保留敏感输入的文本、拼音和次数，后续正常输入触发阈值时一起入库。单纯检查“敏感输入后数据库为空”发现不了这个问题。

**解决方案**：在进入任何造词、历史跟踪和学习状态更新前应用学习权限判断；关闭学习时不新增共享统计，清除当前会话的 partial、consecutive 和待处理取字状态。敏感模式切换与普通学习开关都要走同一入口，已有正常模式的共享统计可以保留，敏感输入不得贡献计数。不要通过关闭所有正常造词功能来绕过问题。

**验收**：敏感两遍 + 正常一遍不得造词；随后累计三遍正常输入才形成；敏感状态跨 provider 也不能影响其他正常会话；关闭再开启学习同样不能补记关闭期间的次数。

## 2. P1：5 万条学习记录下，输入线程出现几十至百毫秒的尖峰

**实际复现**：合成 50,001 条快照（50,000 个英文技术词样式键 + 一个中文键），对同一词连续选用。第二轮实测：

| 操作 | 耗时 |
| --- | ---: |
| 第 31 次 `recordSelection` | 0.000277 ms |
| 第 32 次 `recordSelection` | 54.51 ms |
| 合并后的首次 `recallCandidates` | 69.43 ms |
| 预热后的再次召回 | 0.001843 ms |
| 一次负反馈 | 49.29 ms |

再通过真实 `LearningWriter` 载入 50,000 条记录，另一 SQLite 连接持有 `BEGIN IMMEDIATE` 模拟写入暂时被占用，连续运行 128 次入队和随后召回；输入侧组合耗时经验 P99 为 **118.44 ms**，解除占用后 `flush()` 成功。这不是全栈 GUI P99，也不是每次输入都慢；它证明查询预热后的微秒级指标掩盖了输入侧的周期性尖峰。性能数字依赖本机、数据分布和调度。

**根因**：`core/src/learning_snapshot.cpp:607` 每 32 次选择执行全量 `consolidate()`；负反馈和屏蔽也立即全量合并。合并重建基础索引后在 `:730` 丢弃召回索引，下次输入再通过 `ensureRecallIndex()` 全量构造。`LearningWriter::enqueueSelection` 在输入线程及 `mutex_` 内执行快照更新，因此“异步写库”不能消除这些同步成本。后台每批成功后又 `readState()` 全表读取并重建快照，也应避免与输入侧争锁及重复处理。

**解决方案**：输入线程只更新有界增量和增量召回索引；后台执行合并、剪枝与完整索引构建，再一次发布不可变快照。发布必须以事件序号/存储重置代次为依据，重放尚未覆盖的增量，防止丢选词、重复计数或清空后复活。旧快照的大对象释放也移出输入线程的锁区。不可简单把 32 调大，因为只会延后尖峰并放大增量扫描。

**验收**：增加 `LearningWriter/Controller` 级 50k、200k 连续提交与下一键召回基准，包含第 32 次、删词、负反馈、写锁占用及重置场景；保留演化文档原有查询 P99 <1 ms 门禁，并单独约束提交延迟与长尾。

现有 `BM_RecordUsage_HotPath_50k` 只反复更新一个无持久化的 `PersonalEngine` 词条；现有百分位门禁主要测 `PersonalEngine` 查询与五候选重排，不覆盖应用使用的 `LearningWriter + LearningSnapshot` 合并路径。

## 3. P1：LMDB 批量失败后已有事件已提交，重试重复计数

**实际复现**：向同一批次放入正常 `你好` 记录和 600 字节文本记录。LMDB 的 DUPSORT 值大小限制导致第二项写入失败。`recordBatch()` 返回 false，但 `你好` 已经 frequency=1；重试整批再次失败，`你好` 变为 frequency=2。同样数据在 SQLite 可正常提交；此对照不代表 SQLite 注入了失败。

**根因**：`core/src/learning_store.cpp:470` 的 LMDB 分支逐事件调用 `RecordUsage`，而后者通过 `PersistVariantToLmdb` 每次独立提交事务。失败后的 `ReloadFromLmdb()` 只能重新读取，不能回滚已提交的前半批。`LearningWriter` 会把失败批次整体重试。当前 reset revision 的检查也不与整批写入处于同一事务。

**解决方案**：整批修改、reset revision 检查、上下文/容量清理必须放进一个 LMDB 写事务；只在提交成功后发布内存状态。失败 abort 全批，扩容后重试整个事务。对不支持的超长记录在事务前明确校验，或调整 DUPSORT 数据布局；不能仅丢弃坏项来掩盖非原子性。

**验收**：第 N 项故障、提交故障、扩容、清空交错等场景，失败后前 N−1 项频次不变；成功重试各计一次；内存与重启后磁盘一致。

## 4. P2：移动光标及连续删除整词会误触发“三次取字提权”

**实际复现 A**：提交“你好”，周边文本先为 `before=你好, after=''`，随后仅把光标左移一字，变为 `before=你, after=好`，没有任何删除。数据库却给“你好”增加一次负反馈，给“你”增加 frequency=3。

**实际复现 B**：提交“你好”，按两次 Backspace，依次回报 `你`、空串；中途剩一个字时已经把“你”学习三次，随后整词删完无法撤回。

**根因**：`adapter/fcitx5/src/engine.cpp:193` 的识别只比较周边文本与原词的子串；未证明发生了删除，也未验证光标两侧合起来仍是原词。`:304` 一旦匹配单字即立即注入三次事件，并使 recent commit 失效。

**解决方案**：记录删除按键/编辑意图和原文档局部窗口，先区分纯光标移动与文本删除。单字剩余先进入待确认状态；下一次非删除输入时确认学习，继续删除到空则取消。保留文档规定的中间字提取能力与下一次输入即提权体验，无法证明删除的应用回报应放弃推断，快捷键取字仍可直接学习。

**验收**：词内任意光标移动不学习；连续逐字删完整词不学习任何中间残字；真正退格留字后下一次输入仍能达到原文档规定的排位。

## 5. P2：有效空上下文被当作“没有上下文”，已删除文字参与下一词学习

**实际复现**：上例删空“你好”后输入“世界”。数据库记录 `世界 / shijie / context_before=你`，尽管宿主文本已经为空。

**根因**：`adapter/fcitx5/src/engine.cpp:382` 在 `before` 和 `after` 都为空时恢复 `fallbackContextBefore_`，既不处理完整删除，也不清除回退文本。合法空文档、换行后空上下文和客户端不支持 surrounding text 被压成同一种表示。

**解决方案**：上下文接口显式携带“有效/不可用/边界失效”状态；有效空串必须覆盖并清空旧上下文，完整删除也要送入反馈状态机；只在确实没有 surrounding text 支持且连续性可证明时使用回退。换行、失焦和光标跳转要独立使回退历史失效。

**验收**：清空文档、换行到空行、跳至空位置后，下一词无旧上下文；不支持 surrounding text 的应用仍能在同一连续输入中使用有界回退。

## 6. P2：持久化屏蔽没有覆盖全部候选来源

**实际复现**：

- 删除“你好”，当前 provider 首选变为“拟好”；数据库确有 `suppressed=1`；重新创建 provider 后首选仍是“你好”。
- 输入 `gara` 删除补全 `garage`，刷新后 `garage` 仍为首选。
- LMDB 给带上下文的“你好”增加通用屏蔽，精确查询返回 0 项，前缀查询仍返回 1 项。

**根因**：原生候选管道未用持久化 `isSuppressed` 过滤，Provider 主要依赖本会话 `suppressedLearned_`；静态英文预测 `pinyin_candidate_provider.cpp:2063` 未经过与学习英文相同的过滤；LMDB 前缀查询 `personal_engine.cpp:1078` 只看当前变体自己的 suppressed 标记，没有聚合通用屏蔽。

**解决方案**：统一候选身份和屏蔽判断，在系统词典、学习召回、英文静态/个人补全、LMDB 精确/前缀结果合流时应用同一持久化屏蔽语义。保持正常重新主动选用时解除屏蔽的既有语义；不要仅扩大会话集合生命周期。

**验收**：当前会话、新 provider、共享资源另一个输入上下文、重启后行为一致；含上下文变体和英文静态补全均不得绕过屏蔽。

## 7. P2：英文补全按输入前缀入库，个人英文召回读不到

**实际复现**：输入 `gara`，选择 `garage`，数据库记录 `phrase=garage, pinyin=gara, frequency=1`。对学习快照调用 `recallEnglishWords('gar')` 返回 0 项。

**根因**：`pinyin_candidate_provider.cpp:2140` 附近把补全候选标为 Raw，并设置 `fullPinyin=rawInput`；提交沿用这个前缀。`LearningSnapshot::recallEnglishWords` 则按 `(phrase, phrase)` 判断正频次。写入键与读取键不一致，频次会分散在各个前缀。

**解决方案**：为英文补全使用明确的提交角色和完整单词学习键，保留 `rawKeystrokes`、`consumedInputBytes` 记录真实输入消费范围；原文 Enter 仍保留原文行为。历史前缀记录可按明确的英文补全判据归并，避免修改同形中文或用户自定义映射。

**验收**：从多个前缀选择同一完整单词，累加同一词条；未出现在静态词典的个人术语可再次按不同前缀召回；`de` 中文首选保护、英文双元音和中文简拼不退化。

## 8. P2：启动时存储不可用，路径恢复后学习仍无法自行落库

**实际复现**：用一个普通文件占据数据库父路径，构造 `LearningWriter` 使首次打开失败；随后将测试父路径修复为目录。新的 `enqueueSelection()` 返回 false，`flush()` 返回 false，数据库也没有创建。内存可短暂体现学习，但没有持久化恢复。

**根因**：`core/src/learning_writer.cpp:94` 在 `!storageAvailable_ && !processing_ && events_.empty()` 时直接拒绝持久化入队；worker 没有事件便不会尝试重开。已有非空失败队列的重试机制无法覆盖首次打开失败的空队列状态。

**解决方案**：不可用时仍接纳有界事件队列，在后台按退避重试打开；新输入可触发下一轮有界恢复，输入线程只做内存更新。保留队列容量约束、flush 有限等待与 reset revision 防复活机制，并提供可观察的持久化健康状态。

**验收**：启动权限/挂载/路径暂时异常，修复后无需重启即可落库；故障期间内存有界；永久失败不死锁；清空前事件不因恢复而重新出现。

## 9. P2：LMDB 上下文变体剪枝仅改内存，重载后复活

**实际复现**：同一词写入 9 个不同上下文；`GetTotalEntries()` 为 8，`ReloadFromLmdb()` 后恢复为 9。

**根因**：`core/src/personal_engine.cpp:546` 附近删除内存 vector 中的被淘汰变体；`:566` 只持久化本次目标，没有从 LMDB 删除被淘汰的旧变体。当前快照还可能隐藏多余项，掩盖磁盘持续累积。

**解决方案**：淘汰变体与本次写入在同一事务里执行精确 `mdb_del`，事务成功后再更新内存。修复后提供后台一致性清理旧的超额上下文变体，保持每词通用项加最多 8 个上下文项及总体 200,000 容量准则。

**验收**：反复写入并重载超过 8 个上下文后，内存、磁盘游标、设置统计和重启结果一致；失败时保留原有数据，不产生半次剪枝。

## 建议实施顺序与防退化验收

1. 先修敏感模式学习入口、删除反馈状态机与有效空上下文。验收目标是“不把未表达的用户偏好写入库”。
2. 修整批事务、屏蔽一致性、英文键、上下文剪枝及启动恢复。SQLite 与 LMDB 应共享同一存储契约测试，不仅检查各自简单成功路径。
3. 将快照合并/索引构建移至后台，增加输入侧延迟基准。优先解决线性规模工作，不凭感觉提高学习权重或降低容量。
4. 每项修复先把上述复现转为失败回归；实现后运行全量 CTest、GTest、Benchmark 和 `./tests/verify_fresh_clone.sh`，同步 README、算法演化记录与交付记录。维持 200,000 容量、中文短拼保护、半衰期模型、真实取字提权、分段消费对齐等既有约束。

本轮已重新构建当前代码，运行 7 项相关 CTest（学习存储、拼音 Provider、英文仲裁、日常模拟、控制器集成、PersonalEngine GTest、Benchmark），全部通过，耗时 26.55 秒。另运行两轮独立回放，第二轮增加敏感模式对照及写锁延迟场景。没有修改算法，所以没有执行发布、安装或算法特性台账追加；通过的旧测试不代表本报告发现的问题已经修复。
