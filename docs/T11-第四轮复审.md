## 2. V1 / P0：LearningStore生产剪枝策略未经授权改成80%

位置：`core/src/learning_store.cpp:55–59,71–73`。

本提交将LearningStore LMDB门面的剪枝目标由 `totalEntryLimit_` 改成 `totalEntryLimit_ * 4 / 5`，同时作用于默认打开和设置容量。

现行契约明确保留用途差异：

- `docs/算法架构.md:142`：Snapshot/SQLite保留到上限；LearningStore的LMDB门面容量与剪枝目标均设为上限。
- `docs/算法演化记录.md:121`：独立PersonalEngine默认目标160k；LearningStore LMDB门面保持容量上限；不得在重构中悄悄统一差异。

因此默认200k门面现在被配置为超限剪到160k。这是额外删除历史数据的行为变化，不是基准夹具参数；没有改变schema或名义max值不能证明保留行为不变。

### 已复现

容量设为5，分别在**独立目录**创建SQLite与LMDB库，顺序提交不同词。独立目录用于排除自动SQLite→LMDB迁移干扰。

```text
learning.sqlite3 inserted=5 retained=5 expected_baseline=5
learning.sqlite3 inserted=6 retained=5 expected_baseline=5
learning.sqlite3 inserted=8 retained=5 expected_baseline=5
learning.lmdb inserted=5 retained=5 expected_baseline=5 physical=5
learning.lmdb inserted=6 retained=4 expected_baseline=5 physical=4
learning.lmdb inserted=8 retained=4 expected_baseline=5 physical=4
```

`physical`来自PersonalEngine物理状态计数，排除了仅快照显示限额造成的差异。200k→160k是同一配置公式的默认影响，本轮没有再写满200001条默认库。

### 最小整改与验收

- 恢复LearningStore原有剪枝策略。独立PersonalEngine已有160k策略保留。
- 基准需要发生真实剪枝，应在原政策下明确触发并验证淘汰；若夹具确需特殊目标，必须只显式作用于夹具，不能改变生产默认。

## 3. V2 / P1：新增Writer容量setter跨越后台存储所有权，TSAN已复现竞争

位置：`core/src/learning_writer.cpp:222–226,432–433`；实际竞争字段读写：`core/src/learning_store.cpp:478` 与 `:56`。

`LearningWriter::setTotalEntryLimit` 持输入mutex，直接修改store对象。后台持storeMutex执行recordBatch/prune，未持同一输入mutex；两个锁不能保护同一字段。Writer自身 `totalEntryLimit_` 也在persistBatch中以另一同步边界读取。

独立合成SQLite库中，一线程调用新增setter，同时正常入队并后台写入；使用当前TSAN核心库与：

```bash
setarch x86_64 -R env TSAN_OPTIONS=halt_on_error=1 /tmp/modernime-t11-config-race
```

退出66，关键报告为：

```text
WARNING: ThreadSanitizer: data race
Read: LearningStore::pruneTotalEntries() learning_store.cpp:478
Previous write: LearningStore::setTotalEntryLimit() learning_store.cpp:56
Caller: LearningWriter::setTotalEntryLimit() learning_writer.cpp:226
```

目前新增setter的仓库调用点主要是基准初始化；本复现验证的是公开API与后台工作交错，**不声称普通输入在不调用setter时必然出现竞争**。原31项核心并发测试不覆盖该新增调用，不能据此宣布新API无竞争。

### 最小整改与验收

- 若只为基准配置所需，优先将参数限制为worker启动前的不可变配置，移除运行期跨线程直接写store的入口。
- 若确需运行期更改，遵守单一后台写入者与统一同步/锁序，配置生效和后台批次之间应有明确边界。
- 不要在现有输入mutex内直接再加storeMutex：先检查 `reload()` 等store→input锁序，避免修竞争又引入锁反转。
- 对新API实际允许的生命周期补并发或初始化契约测试，用TSAN复跑独立交错和已有Writer套件；SQLite/LMDB均检查。
