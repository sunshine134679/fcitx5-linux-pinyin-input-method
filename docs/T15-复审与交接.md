## 2. R1 / P1：LearningPage 没有请求代次与操作状态，旧统计可覆盖新状态并重新放行清空

**位置：** `tools/settings/pages/learning_page.cpp:115–160,222–276`。

LearningPage 的 RefreshTaskData 没有 generation。每个完成回调只检查页面是否还活着，就按自己的 count 直接修改清空按钮。onClear 仅置灰按钮，没有一个独立于展示控件的进行中操作状态；它也不检查是否已有清空任务。

这是同步改异步后新增的顺序/所有权问题。`DiagnosticsLifetime` 只能阻止访问已析构 Impl，不能判断结果是否过时，也不能防止旧读结果授权第二次写操作。

### 独立真实 GTK 复现 A：旧统计覆盖新统计

探针链接 T15 当前生产 LearningPage、DataController、core 对象，通过测试可执行文件的链接包装器，在真实 SQLite COUNT 返回结果后暂停第一个统计请求，不修改业务实现。

1. 私有数据库含 1 条，页面初始化完成。
2. 第一次 refresh 已读到 1，暂停其返回。
3. 将私有数据库清空，第二次 refresh 完成，count=0，按钮置灰。
4. 放行第一次 refresh，旧 count=1 重新启用按钮。

```text
newer_empty_result_button=0
old_result_overrode_new=1 final_button=1
```

### 独立真实 GTK 复现 B：清空进行中被旧统计重新启用，第二个任务真实进入

在真实 `sqlite3_backup_step` 之前设置栅栏，阻塞第一个备份/清空 worker。此时放行先前已读到 1 的 refresh 完成回调，然后对已经重新启用的按钮走真实确认对话框与点击回调：

```text
during_first_clear_button=0 backups=1
pending_refresh_reenabled=1
simultaneous_clear_backups=2
```

第二次 backup_step 在第一个仍未放行时进入，因此是两个同时在途的清空任务，不是同一备份循环的两次调用。放行后实际记录了两个清空完成。全部数据和备份均在探针私有目录，本次没有宣称复现真实用户数据丢失；并发清空可能使确认、备份与新学习事实的边界失去预期顺序。

### 推荐目标与完成标准

- 在既有 LearningPage 内明确当前读请求代次和单个进行中变更操作；按钮状态由这些事实派生，不能作为操作权限的唯一事实。
- 旧代统计完成不得覆盖新结果；清空开始时作废先前统计，清空完成后再发起新统计。错误完成也必须受相同代次约束。
- 清空 handler 自身拒绝重入；任意旧统计/刷新完成都不能在变更操作结束前放行第二个备份/清空。
- 页面关闭作废 UI 回调，但不破坏已经进入 Store 的备份/清空事务。保留备份失败不清空、原学习世代/格式/容量契约。
- 将上述两种交错固化为先失败、修复后通过的测试。无需引入全局 DataManager、通用调度框架或借用包管理状态机。

## 4. R3 / 验收阻断：慢 I/O 与连续打断没有命中声称的生产交错

**位置：** `tests/settings/settings_data_async_gtk_test.cpp:430–520` 及 `docs/T15-验收报告.md`。

### 4.1 两秒慢 I/O 是独立睡眠任务

`testLearningPageAsyncAndSlowIo` 先启动一个仅 sleep(2s) 的独立 GTask，等它完成并停止心跳之后，才创建 LearningPage。该 GTask 不调用页面、DataController 或 Store。

因此这里证明 GLib 后台睡眠不阻塞主循环，不能证明生产数据操作在慢 I/O 下仍响应。随后立即关闭页面的测试也没有把真实页面 I/O 固定在这两秒窗口中，更没有执行清空按钮流程。

### 4.2 六次改文本，实际只触发一次 search-changed

现有连续搜索只设置六次文本、短暂 drain/sleep，再以 `0 < rowCount < 20000` 结束，没有验证每轮搜索确实启动，也未精确断言最终查询的行集合。

本轮复制当前提交的测试到忽略目录，只增加 `search-changed` 信号观察计数，链接相同生产页面对象，实际执行：

```text
REVIEW actual_search_changed_signals=1
Max heartbeat latency during continuous search: 30 ms
```

这次运行不能作为“多轮旧渲染被新查询取消”的证据。心跳数值是真实的，但没有覆盖报告所述的打断交错。

### 最小验收补强

- 对真实页的生产读写设置确定性栅栏/延迟，保持慢操作在途两秒，再观察心跳和销毁。测试钩子放最小 I/O 边界，不复制业务逻辑；已进入事务的操作按原契约安全完成。
- 连续搜索须确认每轮生产搜索已触发，至少一次旧批次尚未完成时发起下一轮；断言最终完整行集合/原始索引精确匹配最后查询，旧查询行不能混入。保留搜索时移走原文件的有效证明。
- 覆盖 R1 的乱序读和真正重复清空，以及 R2 的实际慢读写；补实际 worker 在途时的关闭验证。
- 按原计划运行当前 T15 页面/回调的必要 ASAN；本次交付未提供这部分插桩结果，不能由普通测试无崩溃推导“无 UAF 已证明”。不能用其他阶段的 ASAN 日志替代。
- 复用现有新 GTK 目标，由 T16 接线，Release 断言保持启用；无显示跳过与实际运行分开记录，不把手工执行描述成已经注册 CTest。
- 更新验收报告的覆盖范围。“SQLite COUNT(*) 实测 0ms”表示该规模和计时精度下很快，不能仅凭这一次测量把整个接口统一宣称为 O(1)；保留轻量计数、不构造 Snapshot 的真实契约即可。这是文档口径修正，不要求另造计数缓存。
