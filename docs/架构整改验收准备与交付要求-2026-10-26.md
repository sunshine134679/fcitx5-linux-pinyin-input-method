## 二、实施 AI 完成后交什么

不要求为了验收把无关改动强行提交。已提交和未提交实现都可接收，但必须能定位完整源码身份。

| 材料 | 最低要求 |
|---|---|
| 实现位置 | 仓库/worktree 绝对路径、分支、起止 SHA；未提交修改的完整补丁及新增源文件清单 |
| 范围映射 | AR00–AR17 对应 A01–A16、D01–D05 的处理状态；遗漏或未承接项明确列出 |
| 变更说明 | 实际行为变化、状态唯一所有者、兼容/回退影响；与方案不同之处及理由 |
| 回归证据 | 旧版失败/新版结果、真实消费者入口；UB 不能稳定复现时给静态寿命依据，不能虚构红灯 |
| 原始执行记录 | 命令、cwd、环境、实际退出码、完整日志、CTest 注册 JSON、JUnit、原生 GTest XML |
| 配置与产物 | 构建类型/开关、编译器、模型命中及必要产物 hash；原生与插桩、Debug 与 Release 分开 |
| 专项结论 | 安装卸载、并发、备份恢复、容量性能、GTK/桌面及渠道验证的实际范围 |
| 未测内容 | Failed、合法 Skipped、NotRun、Blocked 分开，不能只有“全部通过”的摘要 |

## 三、收到实现后如何验收

### 第一步：确认验收的是交付实现

- [ ] 重新读取 AGENTS、中文命名规范、长期护栏及相关算法契约；核对实施期间规范和需求是否变化。
- [ ] 对比准备基线、实施差异及原有 UI/设置页改动归属；禁止 reset/覆盖用户当前工作树来构造“干净基线”。
- [ ] 固定本轮实际源码、构建配置、模型及产物身份。需要复现旧行为时使用隔离副本，不切换日常工作树或用户数据。
- [ ] 检查是否降低断言、容量、性能要求，或通过跳过消费者、吞退出码、缩小样本获得绿灯。

### 第二步：按问题验证真实行为

下表是关闭条件，具体文件、接口和用例按整改方案对应任务执行。

### 第三步：独立核验验证体系

- [ ] 不只信实施 AI 摘要：读关键差异、测试原断言及真实调用者，独立重跑本轮关键反例。
- [ ] 对修改后的 checker 自身跑正负反例，特别是缺 XML、全部 skipped/disabled、重复名一次失败和过期证据；不能让被修改的验证工具成为唯一担保。
- [ ] 在同一集成源码执行方案第五节的 full/core-only、原生 Release 性能及按影响选择的 Sanitizer；只注册未执行的目标单独列出。
- [ ] 重大架构/安装改动按 AGENTS 执行隔离新鲜克隆安装卸载，核对真实包内消费者；不同渠道、ABI 和旧客户端能力不能互相代签。
- [ ] 有桌面环境时验证真实 GTK/Fcitx 连接；没有时明确未测。未经部署任务不重启日常输入法，不用真实词库或剪贴板作测试夹具。
- [ ] 如需构建/压测，先确认共享 machine.lock 和其他运行任务，避免资源竞争；性能门限继续使用权威规范。

## 四、判定和输出

逐项只使用以下状态：

- **通过**：代码责任与行为正确，要求的实际证据成立。
- **失败**：反例仍成立、原契约退化，或检测器/进程退出非零。
- **待补证据**：实现可能正确，但缺真实消费者、配置身份或原始记录。
- **未验收**：本次未承接/未执行；不得折算为通过。
- **环境阻断**：明确缺失的运行条件及影响范围；不得借此换成较弱验证后全绿。

缺陷修复与精简收益分开判定：某个 D 项暂未做，不抹去已经验证的 A 项修复；但全范围整改结论仍需显式列出未关闭项。方案中的 API 名称不是强制实现形式，只要替代方案保住契约并有对应证据，不因命名不同拒收。

验收报告按“已关闭项→仍存在的问题及优先级→证据→未测范围→下一步”组织，原审查报告保留历史基线。测试数不固定为 78，不能因实施新增测试而要求沿用准备时的数量。
