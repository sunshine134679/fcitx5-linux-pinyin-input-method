## 二、第四轮缺陷修复详情

### 1. R4-01 · P1：共享脏分片物化缓存并发线程安全
- **缺陷现象**：主审快照 ASAN 探针 `快照探针.cpp` 在 8 线程并发调用 `snapshot->entries()` 时触发 AddressSanitizer `heap-buffer-overflow`，原因是多个 `LearningSnapshot` 共享底层 `LearningSnapshotShard` 时，并发调用 `entries()` 竞争无锁的 `materializedEntries_.clear()/push_back()`。
- **根因分析**：分片物化结果的缓存未考虑跨线程并发读取安全性，多个 reader 共享同一个 shard 并发物化时产生内存越界与悬垂指针。
- **治理实施**：在 `core/src/learning_snapshot.cpp` 中定义 `MaterializedCache` 结构体：
  ```cpp
  struct MaterializedCache {
      std::once_flag init_flag;
      std::vector<LearningEntry> entries;
  };
  ```
  每个分片持有 `mutable std::shared_ptr<MaterializedCache> materializedCache_`。在写操作（如 `recordSelection`、`applyDelta`、`consolidate`）时，直接原子重置为全新的 cache；而在只读的 `entries()` 中，通过 `std::call_once(cache->init_flag, ...)` 保证无论多少个 snapshot 实例跨多少个线程并发读取同一个分片，物化逻辑均只被线程安全地执行一次，随后并发只读共享 `cache->entries`。
- **验证结论**：使用 `-fsanitize=address` 重新编译并执行 `build/architecture-fourth-acceptance-20261027/snapshot/快照探针.cpp`，顺序测试与 8 线程高并发测试均 **100% PASS**，AddressSanitizer 报告 0 errors、0 leaks。

### 2. R4-02 / V01 · P1：目标前缀回滚保护既存文件
- **缺陷现象**：安装器归属矩阵校验中，`scripts/modernime-migrate-channel` 在回滚失败事务时，将目标前缀中既存的非本次安装产物一并删除（如测试用既存文件 `share/fcitx5/addon/modernime.conf`）。
- **根因分析**：`cleanup_target_prefix_files` 盲目依据全局清单清理文件，未对“安装前已存在于目标目录的文件”建立基线保护快照。
- **治理实施**：
  1. 在 `scripts/modernime-migrate-channel` 准备阶段，在设置 `package_attempted=true` 之前，扫描目标前缀并记录已存在文件列表：
     ```bash
     target_preexisting_list=$(mktemp)
     # 记录已存在目标文件
     ```
  2. 在回滚函数 `cleanup_target_prefix_files` 中，比对 `$target_preexisting_list`，跳过所有在迁移前已经存在的文件；
  3. 向安全删除校验函数 `modernime_is_safe_removal_target` 传递正确的系统前缀标识，保证 Fail-Closed。
- **验证结论**：执行 `python3 build/architecture-fourth-acceptance-20261027/installer/第四轮定向补验.py`，全部 12 项用例 100% 通过（`PASS: 12, FAIL: 0`）。

### 3. R4-03 / V03 · P1：基线删除识别同一词条的新写与并发选择
- **缺陷现象**：第四轮存储探针中，`concurrent_existing_update` 与 `concurrent_prune_existing_update` 发生数据丢失。当维护线程准备清理旧记录时，另一并发写者重新选择了该词条（频次更新、时间戳更新），但由于原维护基线仅按字符串身份比较（`key + text + context`），误将更新后的词条判为“旧词条”并在提交时从磁盘删除。
- **根因分析**：`baseline_entries_` 仅存储 `std::unordered_set<std::string>` 身份字符串，缺乏读取版本/元数据事实。当词条存在于基线但已被并发写者修改为新事实时，无法感知事实变更，导致 `FlushToLmdb` 将新事实误删。
- **治理实施**：
  1. 在 `core/include/modernime/core/personal_engine.h` 中定义 `BaselineFact`：
     ```cpp
     struct BaselineFact {
         uint32_t hit_count = 0;
         int64_t last_selected_ms = 0;
         bool suppressed = false;
     };
     ```
     将 `baseline_entries_` 升级为 `std::unordered_map<std::string, BaselineFact>`；
  2. 在 `ReloadFromLmdb`、`RecordLearningBatch` 及 `FlushToLmdb` 中填充和维护 `BaselineFact`；
  3. 在 `FlushToLmdb` 准备删除磁盘词条时，先比对磁盘当前词条的 `hit_count`、`last_selected_ms` 与 `suppressed` 状态与 `BaselineFact`。若磁盘已发生更新（`disk_updated == true`），则严格予以保护保留，不执行删除。
- **验证结论**：`concurrent_existing_update` 与 `concurrent_prune_existing_update` 成功保留并发新写事实（`updated_fact_preserved=1`）。

### 4. R4-04 · P2：Writer 增量感知并吸收同代外部学习与屏蔽事实
- **缺陷现象**：第四轮存储探针中，`writer_external_sqlite3` 和 `writer_external_lmdb` 断言失败：Writer 实例在初始加载后，另一个独立的真实 `LearningStore` 写入新词、频次增长或新增屏蔽，Writer 自身后续执行写入并 flush 后，其乐观发布的快照未包含这些外部已落盘的事实。
- **根因分析**：`LearningWriter::run` 仅在 `resetRevision` 增长或发生总量剪枝时才调用 `readState()`；而同代的外部写入既不修改 clear revision，也不触发本地剪枝，导致发布快照未能感知外部提交。
- **治理实施**：
  1. **SQLite 机制**：利用 SQLite 原生提供的 `PRAGMA data_version;`（该 pragma 专门用于缓存失效检测：仅当外部数据库连接提交事务时递增，本地事务提交后保持不变）。在 `LearningStore` 中引入 `dataVersion()` 与 `lastDataVersion_` 跟踪；
  2. **LMDB 机制**：利用 LMDB 事务 ID 单调递增特性：在 `PersonalEngine::RecordLearningBatch` 中检测写事务 ID 是否连续（`txn_id != last_lmdb_txn_id_ + 1`），若跳跃则表明发生外部写入；
  3. **数据通道联动**：`RecordLearningBatch` 与 `LearningStore::recordBatch` 增加 `bool *external_changed` 参数，`LearningWriter::run` 在检测到 `externalChanged == true` 时，无缝调用 `freshState = store_->readState()`，并基于包含外部完整事实的新状态发布快照。在普通单写者击键时保持零重读的亚毫秒极速路径。
- **验证结论**：`writer_external_sqlite3` 与 `writer_external_lmdb` 均输出 `ok=1`，外部学习词频更新、新词发现以及屏蔽均被准确发布到快照中。

### 5. R4-05 / V02 · P2：标点兼容词合法迁移与备份自校验
- **缺陷现象**：第四轮存储探针中，`punctuated_empty_pinyin_migration` 报告 `integrity=0 backup_clear=0 error=learning backup could not be verified`。源 SQLite 存在历史词条带句点（如 `"历史词."`），迁移至 LMDB 成功，但因 key 校验拒绝包含标点，导致 `verifySelf()` 校验失败，阻止了正常的备份与清空。
- **根因分析**：`isValidNormalizedPinyinKey` 对键字符的白名单过去仅允许拼音字母、数字与连接符，拒绝了空 pinyin 迁移保留历史文本时可能出现的合法标点字符。
- **治理实施**：在 `core/src/personal_engine.cpp` 的 `isValidNormalizedPinyinKey` 中，将有效键的判定范围规范为：任何非控制字符、非空白、非分号分隔符的合法 UTF-8 字符（包含标点符号如 `.`），与前端词条及历史格式完全对齐。
- **验证结论**：`punctuated_empty_pinyin_migration` 输出 `integrity=1 backup_clear=1 error=`，自校验完全通过。

### 6. R4-06 · P2：LMDB 性能基准计时口径显式计入快照释放
- **缺陷现象**：第四轮复验报告指出，`tests/core/personal_engine_benchmark.cpp` 中 `verifyLmdbWriterLatency` 将局部快照 `snap` 的析构放到了测量区间之外，导致快照释放成本未计入样本计时。
- **治理实施**：
  在 `verifyLmdbWriterLatency` 循环中，将 `snap.reset()` 显式放在计时区间内：
  ```cpp
  const auto t3 = std::chrono::steady_clock::now();
  snap.reset();
  const auto t4 = std::chrono::steady_clock::now();
  double total_us = std::chrono::duration<double, std::micro>(t4 - start).count();
  double release_us = std::chrono::duration<double, std::micro>(t4 - t3).count();
  ```
  同时在 `SampleBreakdown` 中增加 `release` 字段并完整打印 peak sample 成分。
- **性能实测数据（零降规，200,000 规模完整测量）**：
  - **LMDB writer (50,000 entries)**:
    - P99: **372.77 us (0.37 ms)**
    - Maximum: **4,226.47 us (4.23 ms)**
    - Peak breakdown: `total=4226.47 us (enqueue=3864.55 us, snapshot=0.34 us, recall=361.42 us, release=0.16 us)`
  - **LMDB writer (200,000 entries)**:
    - P99: **254.06 us (0.25 ms)**（远低于 5,000 us 门禁，优于门禁 20 倍）
    - Maximum: **714.71 us (0.71 ms)**（远低于 30,000 us 门禁，优于门禁 42 倍）
    - Peak breakdown: `total=714.71 us (enqueue=46.21 us, snapshot=0.08 us, recall=668.27 us, release=0.15 us)`
