## 2. 必须整改的问题

### R1 / P1：首次非法页面命令没有完成其错误退出契约

位置：`tools/settings/settings_app.cpp` 的 `commandLine()`、`applyNavigationRequest()`。

`commandLine()` 先构造 SettingsWindow；`applyNavigationRequest()` 又在解析 page 之前 present。首次运行 `--page invalid_dummy_page` 虽输出诊断并从回调返回失败，应用仍持有活动窗口，进程继续运行。本轮独立会话探针在 4 秒观察期限后仍未退出，由测试终止私有进程组。4 秒是探针观察上限，不是建议新增的生产超时。

目标：先验证请求，再创建/展示窗口。首次无效页应自行以确定性非零退出；已有实例收到无效页时，次级调用非零退出，原窗口与当前页面保留。不要通过关闭已有主实例、增加业务 kill 超时或吞掉错误解决。

前置测试：分别覆盖无主实例、有主实例两条真实二进制路径，检查退出状态、诊断、窗口/页面副作用；原实现应在首次非法页场景失败。成功路径继续验证正常拉起与单实例转发。

### R2 / P1：DBus 验收脚本不能证明页面和 target 到达主实例

位置：`tests/settings/settings_navigation_dbus_test.sh`。

当前脚本只检查 primary PID 存活、secondary 命令正常返回，以及 stderr 包含未知页文字。它不观察主实例的 GtkStack 可见页、目标控件焦点、主实例身份或窗口数；负向调用还用 `|| true` 丢弃退出状态。固定 sleep 1 也不是已注册就绪证明。

确定性反证：本轮编写一个没有 GTK、没有 DBus、没有路由的假程序：overview 只 sleep，其他正常参数直接返回 0，非法页打印预期文字但也返回 0。**现有正式脚本仍 exit 0 并宣布全部通过。** 证据见 `build/t18-review-evidence/dbus-fake-positive.log`。

目标：保留隔离 DBus 会话，实际观察生产主实例的页面/target 生效及单实例身份；采用有界就绪握手。可使用适合现有测试设施的控件观察或窄测试接缝，但不能仅回显收到的 argv 来证明 UI 已应用。拒收不导航、丢 target、另开窗口、非法页 exit 0 的对照变体。

补齐边界：显式传入必需 binary 不存在应失败，不应寻找其他工作树旧产物或记为图形环境跳过；缺显示才按允许的 77 跳过。清理责任应由拥有 primary 的同一沙箱进程承担，失败分支也有界排空和清理，仅操作本测试资源。无需引入新的生产进程框架。
