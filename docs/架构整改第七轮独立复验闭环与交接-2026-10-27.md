## 二、第七轮缺陷物理根因修复与校准详情

### 1. R7-01 · P1：保护目录及其受保护后代，严禁递归删除包含用户数据的父级目录
- **缺陷现象**：当显式配置的用户数据目录（`$data_dir`）嵌套于本次新建的程序父目录（例如 `MODERNIME_DATA_HOME=<target>/share/modernime/pinyin`，`data_dir=<target>/share/modernime/pinyin/modernime`，而 `pinyin` 为本次安装新建）时，前版脚本在 `cleanup_target_prefix_files` 中深度遍历仅识别到数据目录本身及其子项（跳过删除），但随后遍历到未在基线中的新父目录 `pinyin` 时，因 `pinyin` 本身不是数据目录，直接对其执行了 `rm -rf -- "$item_path"`，导致刚刚保护的子目录及新建独立用户数据随之全量丢失。
- **根因分析**：
  1. 路径判定仅检查了“条目是否为用户数据或其子项”，遗漏了反向关系——“条目是否为用户数据或用户配置的祖先”。
  2. 深度遍历清理中，非基线目录直接使用 `rm -rf` 属于危险的递归强力删除；一旦某个父目录被判定为非基线，即使其深层子节点被跳过保护，父目录的 `rm -rf` 依然会将其斩草除根。
- **治理实施**：
  1. **引入祖先级受保护判定**：在 `scripts/modernime-migrate-channel` 中实现 `modernime_dir_contains_user_data` 函数：
     - 使用 `readlink -m` 规范化路径；
     - 检查目标路径是否与 `$config_dir` 或 `$data_dir` 相等，或者是否为 `$config_dir` 或 `$data_dir` 的祖先父级（`"$canon_data" == "$canon_p"/*`）；
     - 凡包含或可能包含用户数据/配置的路径，严格判定为保护路径。
  2. **深度遍历清理彻底消除 `rm -rf`**：
     - 深度遍历扫描时，同时检查 `if modernime_is_user_data_path "$item_path" || modernime_dir_contains_user_data "$item_path"; then continue; fi`；
     - 对非基线条目区分文件与目录：
       - 若为普通文件/符号链接：执行 `rm -f -- "$item_path"`；
       - 若为目录：**仅使用 `rmdir -- "$item_path"` 安全尝试移除空目录**，绝对禁止 `rm -rf`。若目录内因包含受保护的用户数据或文件而未清空，`rmdir` 遵循 POSIX `ENOTEMPTY` 规范安全失败并保留完整目录及子项；
     - 对顶层 `$pfx/share/modernime`，仅在不包含用户数据且全部程序文件清空后才尝试 `rmdir`，彻底杜绝误删。
- **验证结论**：
  - 运行 `第七轮用户目录嵌套与程序回滚探针.py`：
    - `repository_new_payload_parent`：PASS（`parent_exists=true`，`user_value='independent-new-user-fact'`，`dictionary_value='xin\t新词\t1\n'`，`product_exit=1`）；
    - `generated_new_payload_parent`：PASS（生成入口表现完全一致）；
    - 既有父目录、外部数据及程序 payload 对照共 8 项场景 **8/8 PASS (100%)**。

### 2. R7-02 · P2：必需预备份复制失败时立时中止，绝不进入破坏性源卸载与包改写阶段
- **缺陷现象**：迁移脚本在 Step [3/5] 进行目标既有文件逐项预备份时，在 `cp` 前先将条目写入 `target_preexisting_list`，随后使用 `cp -a ... 2>/dev/null || true`。当 `cp` 遭遇 I/O 错误（如退出码 74）时，错误被丢弃，条目仍被记录为已备份，脚本继续向下执行源端卸载（Step [4/5]）与包安装（Step [5/5]），导致目标原文件在未完成备份的前提下被改写或丢失。
- **根因分析**：预备份阶段缺乏 Fail-Closed 事务防护；把“尝试备份”当成了“已备份完成”，忽视了 I/O 复制阶段可能出现的硬件或权限异常。
- **治理实施**：
  1. 彻底移除预备份阶段的所有 `2>/dev/null || true`；
  2. 严格检查每一个 `mkdir -p` 与 `cp -a` 操作：
     - 若 `mkdir -p` 或 `cp -a` 失败，立刻捕获其真实退出码 `cp_ec`；
     - 向 stderr 输出诊断日志，告警预备份未完成；
     - **完整保留 `$temp_work` 事务材料与已有现场，严格跳过清理**；
     - **直接以该错误码（如 exit 74）中止脚本退出**；
     - **绝不调用源端卸载（Step [4/5]），绝不调用目标包命令（Step [5/5]）**；
  3. 仅在 `cp -a` 或目录创建真正返回 0（成功）后，才将对应路径追加记录至 `target_preexisting_list`。
- **验证结论**：
  - 运行 `预备份与目录属性探针.py`：
    - `repository_prebackup_plugin_cp_failure`：PASS（`copy_hit=True`，`exit=74`，`package_invoked=False`，`target=target-original`，`source=source-original`）；
    - `repository_prebackup_directory_child_cp_failure`：PASS（`copy_hit=True`，`exit=74`，`package_invoked=False`，`target=target-original`）；
    - `generated_*` 生成入口与 `sixth_control_*` 第六轮源码对照全部一致通过（退出码 74，包未调用，原文件完整保留）。

### 3. R7-03 · P3：程序目录属性与纳秒时间戳物理还原
- **缺陷现象**：前版预备份为避开用户数据，对目录改为 `mkdir -p` 与 `chmod --reference` 手工创建，导致备份目录的 `mtime` 变为当前时间。回滚恢复时，整体拷贝将备份创建时刻的时间戳覆写到目标目录，使得原程序目录的纳秒级 `mtime`（如 `1600000000123456789`）无法精准还原。
- **治理实施**：
  1. 在预备份阶段建立专用引用快照目录 `$temp_work/target_mtime_refs` 与元数据清单 `$temp_work/target-dir-mtime.txt`；
  2. 当遍历并备份目标程序目录时，通过 `touch -r "$dir_path" "$ref_file"` 与 `chmod --reference="$dir_path" "$ref_file"` 冻结该目录原始权限与纳秒时间戳；
  3. 在 `restore_original_channel` 阶段，待 `cp -a --remove-destination` 完成全部文件恢复写入后，遍历元数据清单：
     - 检查目标目录，若其为用户数据目录或包含用户数据（`modernime_dir_contains_user_data`），**严格跳过时间戳还原**，确保不覆写迁移期间独立用户的新写事件；
     - 对纯程序目录，使用 `chmod --reference="$ref_file"` 与 `touch -r "$ref_file"` 精准还原其原始权限位与纳秒级 `mtime`。
- **验证结论**：
  - 运行 `预备份与目录属性探针.py`：
    - `repository_directory_attributes_control`：PASS（`directory_after={'mtime_ns': 1600000000123456789, 'mode': 489}`，与 `before` 完全一致）；
    - 生成入口及对照组全部精准匹配。

### 4. R7-04 · P3：区分“无用户数据需备份”与“恢复失败”，消除无用户数据时的虚假报警
- **缺陷现象**：在回滚恢复时，脚本无条件调用 `modernime-data-guard --restore`。但在完全没有用户词典、学习库或配置的干净环境下，`--pre-upgrade` 正常返回 `None` 且不生成 `backups/latest` 链接；而无条件调用的 `--restore` 因找不到 `latest` 抛出异常，导致脚本误报 `User data-guard restore reported errors` 并虚假判定回滚失败保留事务目录。
- **治理实施**：
  1. 在 Step [2/5] 备份执行完成后，明确检测本次事务是否真正创建了有效用户备份：
     - 检测 `$data_dir/backups/migrate-$ts/backup-manifest.json` 是否存在，置位 `user_backup_created=true/false`；
  2. 在 `restore_original_channel` 中：
     - **仅在 `user_backup_created == true` 时才调用 `modernime-data-guard --restore`**；
     - 若确有备份且恢复失败，依然保持 Fail-Closed 严格告警并保留事务材料；
     - 若原本就没有用户备份，正常跳过用户数据恢复，源与目标程序文件恢复成功后整洁退出并清理临时目录。
- **验证结论**：
  - 在无用户数据的干净程序回滚场景下，回滚正常输出 `Original installation restored (channel=script, ...)`，退出码为包失败的预期非零码，绝无虚假数据损坏告警，事务目录整洁销毁；
  - 真正发生数据损坏时依然严密告警并保留全部材料。
