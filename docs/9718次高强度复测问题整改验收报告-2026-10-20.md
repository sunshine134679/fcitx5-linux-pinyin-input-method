## 三、各专项整改深度分析与证据

### 3.1 H1：英文偏好增益饱和后的首选可达性与双向切换

#### 1. 根本原因
- 在 `core/src/learning_snapshot.cpp` 中，英文候选排序分数为 `item.score = baseBoost + completeness`。
- 当旧词（如 `compute`）与新词（如 `computer`）均达到饱和增益 3.9 时，静态补全奖励产生差距：
  - `compute`: $3.9 + 5/7 \approx 4.6143$
  - `computer`: $3.9 + 5/8 = 4.5250$
- 静态补全奖励导致即使选择 `computer` 250 次甚至 5000 次，`computer` 仍因 0.0893 的静态长度差距永久排在 `compute` 后面。同时，英文不使用中文会话级 `RecentChoices`。

#### 2. 解决方案与契约
- 在 `struct RecalledEnglishWord` 中引入 `double baseBoost = 0.0;`。
- 在 `LearningSnapshotShard::recallEnglishWords` 和 `LearningSnapshot::recallEnglishWords` 中引入**竞争休眠折减机制（Competitive Dormant Discount）**：
  - 扫描所有召回的英文候选，提取最新选择时间 $T_{\text{latest}}$ 及对应增益 $B_{\text{latest}}$；
  - 对历史较旧的竞争对手（$T < T_{\text{latest}}$），在成熟习惯（$B_{\text{latest}} \ge 1.8$）确立后，施加基于竞争时间差与增益的衰减，折减系数最高下探至 $0.70$（$3.9 \times 0.70 = 2.73$）；
  - 偶选单次（$B = 0.939 < 1.8$）不会激活竞争休眠，旧首选稳如磐石；当连续选择新词 $\ge 10$ 次（$B \ge 2.93$），旧词增益折减至 $2.73$，$2.73 + 5/7 \approx 3.444 < 4.525$，新词以压倒性优势登顶首选；
  - 该事实直接由现有 SQLite/LMDB 持久化词频与时间戳推导，无需任何 Schema 变更或临时状态。

### 3.2 H3：消除并列最新时间戳的枚举依赖

#### 1. 根本原因
- `CandidateRanker::rank` 中维护 `latestByPriority`（类型为 `unordered_map<int, pair<int64_t, double>>`），记录每个匹配优先级下的最新选择时间及其学习增益。
- 旧实现：
  ```cpp
  if (candidate.last_selected_ms > entry.first) {
      entry.first = candidate.last_selected_ms;
      entry.second = candidate.learning_boost;
  }
  ```
- 当两个不同候选具有相同毫秒时间戳（如批量落库、合成回放或同毫秒操作）时，如果后遍历到的候选时间相等，旧逻辑直接忽略后者的增益。导致若“是”与“试”时间戳并列，首选完全由输入容器的排列顺序（Permutation）或哈希遍历顺序决定。

#### 2. 解决方案
- 采用**确定性单调可结合规约（Monotonic Semilattice Reduction）**：
  ```cpp
  if (candidate.last_selected_ms <= 0) continue;
  auto &entry = latestByPriority[candidate.match_priority];
  const double boost = std::isfinite(candidate.learning_boost) ? std::max(0.0, candidate.learning_boost) : 0.0;
  if (candidate.last_selected_ms > entry.first) {
      entry.first = candidate.last_selected_ms;
      entry.second = boost;
  } else if (candidate.last_selected_ms == entry.first) {
      entry.second = std::max(entry.second, boost);
  }
  ```
- 严格规避 NaN 与负数非法增益，且对全部 6 种输入排列及 SQLite/LMDB 不同写入顺序完全同构。

### 3.3 H2：推广不同长度输入的未学习单字前缀可发现性

#### 1. 根本原因
- 在 `algorithm/pinyin/src/candidate_mixer.cpp` 中，未学习单字前缀席位此前被硬编码限制在 `syllablePrefixEnds.size() == 3`（即仅四音节长句有效）。
- 导致三音节（`nihaoma`）、五音节（`woshizhongguoren`）、六音节（`nihaoshijiepengyou`）及七音节（`qingbangwodakaiwenjian`）下，未学首单字（“你”、“我”、“请”）深陷在完整候选之后，需要翻 10~16 页（40~60+ 位）。

#### 2. 解决方案与席位编排契约
- 在 `candidate_mixer.cpp` 中，将资格条件推广至所有音节切分：
  ```cpp
  singlePrefixQualified = (personalPrefix == nullptr) && (oneSyllable != nullptr) &&
      std::any_of(partialCandidates.begin(), partialCandidates.end(), [&](const auto &c) {
          return c.text == oneSyllable->text && c.full_pinyin == oneSyllable->full_pinyin;
      });
  ```
- **有界席位分配规则**：
  - **二音节输入**（`ends.size() < 2`）：不套用长句席位，保持原生合理排序，保护常用双字词；
  - **3~6 音节输入**：
    - Slot 1: 最优完整整句候选（`*bestFullSentence`）
    - Slot 2: 二音节前缀候选（`twoSyllable != nullptr ? twoSyllable : threeSyllable`）
    - Slot 3: 次优完整整句候选（`runnerUpFullSentence`）
    - Slot 4: **单字前缀候选（`oneSyllable`）**
    - Slot 5: 同音/单字补充候选（`homophone`）
  - **7+ 音节超长输入**（`ends.size() >= 6`）：
    - Slot 1: 最优完整整句候选（`*bestFullSentence`）
    - Slot 2: 三音节前缀候选（`threeSyllable`）
    - Slot 3: 次优完整整句候选（`runnerUpFullSentence`）
    - Slot 4: 二音节前缀候选（`twoSyllable`）
    - Slot 5: **单字前缀候选（`oneSyllable`）**
  - 后续长前缀候选在 `rawFallback` 之后按序追加，既保护了全拼整句与次优整句在前三位，又确保未学习的单字前缀稳居全局前 5。

### 3.4 H4：简拼次选稳定性诊断与三层消融

在禁学、禁上下文学习、固定空周边文本下，对 `dl` 与 `pyt` 分别回放普通输入、尾部回改与中间插入后撤回各 100 次，并以全新独立进程复核。消融结论如下：

1. **第一层：用户可见交互与首选**
   - `dl` 首选始终为“登录”（rank 1）；`pyt` 首选始终为“朴有天”（全拼/简拼混合首位）或“python”（纯英文补全）；
   - 无论发生何种次选波动，**首选未发生任何变化，未发生按当前页面选错词，消费范围严格保持一致**。

2. **第二层：`pyt`（“排演厅” vs “排云亭”）根因定位**
   - 直接调用 LibIME `PinyinContext::candidates()`，原生引擎对 `排演厅` 与 `排云亭` 计算出的 Lattice 解码代价完全相同（均为 `-17.8573`）；
   - 在图搜索（A* / Heap）提取等分节点时，由于底层堆结构中指针或内部容器遍历微动，LibIME 交替将 `排演厅` 和 `排云亭` 置于下标 27 与 28；
   - 上层 `candidate_pipeline.cpp` 按原生顺序记录 `source_index`，进而被 `base_prior()` 乘上 1.0 的顺序步长惩罚，导致两者在 Ranker 中产生 1.0 的最终代价差。
   - **性质定位**：属于第三方 LibIME 引擎等分格点的原生召回无序，而非 ModernIME 排序重构引入的退化。

3. **第三层：`dl`（“得了” vs “的老”）根因定位**
   - 汉字“得了”具备多音读音：`de'liao`（解码分 -5.199，排名第 5）与 `de'le`（排名第 17）；
   - 在中间编辑 `replaceInput("dl")` 时，LibIME 的内部拼音分词器有时将 `dl` 声母切分为 `de'le`，导致该词落入 LibIME 单字/二元组前 16 项截断之外，未被 LibIME 召回；
   - **性质定位**：属于底层拼音切分器多音字歧义展开的无状态特性。

4. **处理原则**：
   - 保持架构护栏，**不采用“冻结旧列表”、“在内存补捏未召回词”或“无限扩大召回预算”等遮蔽手段**，避免破坏不可变快照及状态单写者契约。将根因及行为边界正式记录入架构文档与演化手册。
